# 订单履约数据字典

本文定义 B 域的五张表及其跨域边界。金额为 `DECIMAL(10,2)`，业务主键为 `BIGINT IDENTITY(1,1)`；历史成交价、促销、实付金额和积分倍率均为快照，不能由当前主数据反算。

## 1. SalesOrder（销售订单）

来源是收银员通过 `dbo.sp_create_order` 提交的商品 JSON；消费者为支付、后厨、配餐、骑手、订单视图和库存接口。禁止业务角色直接写表。

| 字段 | 含义 | 类型/可空/默认 | 键、规则与消费者 |
| --- | --- | --- | --- |
| `order_id` | 订单代理主键 | `BIGINT IDENTITY`，否，无 | PK `PK_SalesOrder`；被明细、支付、配送、积分和库存流水引用。 |
| `order_no` | 外部可见订单号 | `VARCHAR(50)`，否，无 | UQ `UQ_SalesOrder_order_no`；由下单调用方提供，供履约检索。 |
| `customer_id` | 下单顾客 | `BIGINT`，否，无 | FK 至 `Customer`；支付时读取其会员等级倍率。 |
| `order_status` | 订单履约状态 | `VARCHAR(20)`，否，`PENDING_PAYMENT` | CHECK 枚举；由 B 状态机写入。 |
| `fulfillment_method` | 履约方式 | `VARCHAR(20)`，否，无 | CHECK：`PICKUP`/`DELIVERY`；决定完成制作后的下一状态。 |
| `pickup_code` | 自取核销码 | `VARCHAR(20)`，自取否、外送可空，无 | 过滤唯一 `UQ_SalesOrder_pickup_code WHERE pickup_code IS NOT NULL`；自取订单必填。 |
| `total_amount` | 订单应付总额 | `DECIMAL(10,2)`，否，`0.00` | CHECK `>=0`；仅汇总 `SELLABLE` 明细，支付金额必须精确相等。 |
| `ordered_at` | 下单时间 | `DATETIME2(0)`，否，`SYSDATETIME()` | 下单/报表使用；`@ordered_at` 只允许 `test_*` 主体传入。 |
| `paid_at` | 支付成功时间 | `DATETIME2(0)`，可空，无 | `sp_pay_order` 成功时写入。 |
| `production_started_at` | 开始制作时间 | `DATETIME2(0)`，可空，无 | `PAID → IN_PRODUCTION` 时写入。 |
| `production_finished_at` | 制作完成时间 | `DATETIME2(0)`，可空，无 | 实扣库存并转待取/待配送时写入。 |
| `completed_at` | 统一终态时间 | `DATETIME2(0)`，可空，无 | 自取或送达终态写入；驱动积分生效。 |
| `cancelled_at` | 取消/退款时间 | `DATETIME2(0)`，可空，无 | 取消或退款成为 `CANCELLED` 时写入。 |

状态：`PENDING_PAYMENT → PAID → IN_PRODUCTION → READY_FOR_PICKUP → PICKED_UP`，或 `... → READY_FOR_DELIVERY → DELIVERING → COMPLETED`；`PENDING_PAYMENT` 可取消，`PAID`/`IN_PRODUCTION` 可在实扣前全额退款至 `CANCELLED`。所有跃迁只能经 B 过程，并与 C 的锁库、释放或实扣过程同一外层事务完成。

## 2. SalesOrderItem（订单明细）

来源是 `sp_create_order`：该过程调用 A 的 `fn_get_effective_product_price` 写成交价/促销快照，并为套餐根据 `ComboComponent` 自动展开。消费者为订单详情、厨房队列、库存锁定和消耗；禁止直接写入。

| 字段 | 含义 | 类型/可空/默认 | 键、规则与消费者 |
| --- | --- | --- | --- |
| `order_item_id` | 明细代理主键 | `BIGINT IDENTITY`，否，无 | PK `PK_SalesOrderItem`；可被套餐子项自引用。 |
| `order_id` | 所属订单 | `BIGINT`，否，无 | FK 至 `SalesOrder`；订单总额与库存过程按此聚合。 |
| `product_id` | 商品 | `BIGINT`，否，无 | FK 至 `Product`；商品当前改价不影响本行。 |
| `parent_order_item_id` | 套餐父明细 | `BIGINT`，可空，无 | 自 FK 至 `SalesOrderItem`；仅 `COMPONENT` 填写。 |
| `item_role` | 售卖父项/套餐子项 | `VARCHAR(20)`，否，无 | CHECK：`SELLABLE`/`COMPONENT`。单品和套餐父项为 `SELLABLE`；子项为 `COMPONENT`。 |
| `quantity` | 本项数量 | `INT`，否，无 | CHECK `>0`；套餐子项为父数量 × `ComboComponent.quantity`。 |
| `unit_price` | 成交单价快照 | `DECIMAL(10,2)`，否，无 | CHECK `>=0`；只有 `SELLABLE` 参与订单金额，组件固定 `0.00`。 |
| `promotion_id` | 命中的促销快照 | `BIGINT`，可空，无 | FK 至 `Promotion`；组件必须为 NULL。 |

## 3. Payment（支付记录）

来源为 `dbo.sp_pay_order`，消费者为订单详情、退款、对账和积分预计算。每单至多一条，任何直接插入或更新均不属于业务接口。

| 字段 | 含义 | 类型/可空/默认 | 键、规则与消费者 |
| --- | --- | --- | --- |
| `payment_id` | 支付代理主键 | `BIGINT IDENTITY`，否，无 | PK `PK_Payment`。 |
| `order_id` | 对应订单 | `BIGINT`，否，无 | FK 至 `SalesOrder`、UQ `UQ_Payment_order_id`；防重复支付。 |
| `payment_method` | 支付方式 | `VARCHAR(20)`，否，无 | 由收银员传入，例如现金/扫码；仅保存业务方式，不保存完整支付报文。 |
| `paid_amount` | 实收金额快照 | `DECIMAL(10,2)`，否，无 | CHECK `>0`；必须等于订单 `total_amount`。 |
| `payment_status` | 支付状态 | `VARCHAR(20)`，否，`SUCCESS` | CHECK：`PENDING`/`SUCCESS`/`REFUNDED`/`VOIDED`；退款后为 `REFUNDED`。 |
| `paid_at` | 支付成功时间 | `DATETIME2(0)`，否，`SYSDATETIME()` | 与订单 `paid_at` 同事务写入。 |
| `refunded_amount` | 已退款金额 | `DECIMAL(10,2)`，否，`0.00` | CHECK `0 <= refunded_amount <= paid_amount`；第一阶段只能全额退款。 |
| `refunded_at` | 退款时间 | `DATETIME2(0)`，可空，无 | 退款成功时写入。 |
| `third_party_txn_no` | 第三方业务流水号 | `VARCHAR(100)`，可空，无 | 用于对账，不保存支付完整报文、卡号或密钥。 |

支付过程签名：`sp_pay_order @order_id BIGINT, @payment_method VARCHAR(20), @paid_amount DECIMAL(10,2), @third_party_txn_no VARCHAR(100)`。它以显式事务写支付、订单 `PAID` 和一条待生效积分流水；任一步失败必须一起回滚。

## 4. Delivery（配送记录）

来源于 `sp_finish_production`（创建待取记录）及骑手过程；消费者为外送履约视图与骑手权限校验。仅外送订单具有此记录，每单至多一条。

| 字段 | 含义 | 类型/可空/默认 | 键、规则与消费者 |
| --- | --- | --- | --- |
| `delivery_id` | 配送代理主键 | `BIGINT IDENTITY`，否，无 | PK `PK_Delivery`。 |
| `order_id` | 外送订单 | `BIGINT`，否，无 | FK 至 `SalesOrder`、UQ `UQ_Delivery_order_id`。 |
| `rider_employee_id` | 实际骑手 | `BIGINT`，可空，无 | FK 至 C 的 `EmployeeAccount`；待取时可空，取餐时必须与 `USER_NAME()` 解析员工一致。 |
| `delivery_status` | 配送状态 | `VARCHAR(20)`，否，`WAITING_PICKUP` | CHECK：`WAITING_PICKUP`/`DELIVERING`/`DELIVERED`。 |
| `picked_up_at` | 骑手取餐时间 | `DATETIME2(0)`，可空，无 | `sp_pick_up_delivery` 写入。 |
| `delivered_at` | 骑手送达时间 | `DATETIME2(0)`，可空，无 | `sp_confirm_delivery` 写入。 |

过程签名：`sp_pick_up_delivery @order_id BIGINT, @rider_employee_id BIGINT` 只允许 `READY_FOR_DELIVERY → DELIVERING`；`sp_confirm_delivery @order_id BIGINT` 只允许 `DELIVERING → COMPLETED`，并在同一事务让积分生效。

## 5. PointLedger（积分流水）

来源为支付过程的预计算，消费者为顾客积分、会员升级和积分流水视图。B 只负责流水状态；累计积分和等级选择必须调用 A 的 `sp_apply_customer_points`，不得直接更新 `Customer`。

| 字段 | 含义 | 类型/可空/默认 | 键、规则与消费者 |
| --- | --- | --- | --- |
| `point_ledger_id` | 积分流水代理主键 | `BIGINT IDENTITY`，否，无 | PK `PK_PointLedger`。 |
| `order_id` | 来源订单 | `BIGINT`，否，无 | FK 至 `SalesOrder`、UQ `UQ_PointLedger_order_id`；每单最多一笔正向流水。 |
| `customer_id` | 受益顾客 | `BIGINT`，否，无 | FK 至 `Customer`；终态时传给积分接口。 |
| `paid_amount_snapshot` | 实付金额快照 | `DECIMAL(10,2)`，否，无 | 等于支付的 `paid_amount`。 |
| `point_multiplier_snapshot` | 支付时会员倍率 | `DECIMAL(5,2)`，否，无 | 来自支付时顾客当前会员等级，后续改级不回算。 |
| `point_delta` | 本单应得积分 | `INT`，否，无 | CHECK `>=0`；固定公式 `FLOOR(paid_amount_snapshot * point_multiplier_snapshot)`。 |
| `ledger_status` | 流水状态 | `VARCHAR(20)`，否，`PENDING` | CHECK：`PENDING`/`EFFECTIVE`/`VOIDED`。 |
| `created_at` | 预计算时间 | `DATETIME2(0)`，否，`SYSDATETIME()` | 支付成功时写入。 |
| `effective_at` | 生效时间 | `DATETIME2(0)`，可空，无 | 自取/送达终态时写入；退款前未生效则置 `VOIDED`。 |

积分状态：支付成功产生 `PENDING`；`sp_pick_up_order @order_id` 或 `sp_confirm_delivery @order_id` 在外层事务内先锁定并改为 `EFFECTIVE`，再调用 `sp_apply_customer_points @customer_id, @delta`。后者按更新后积分从 ACTIVE 会员等级中选择 `threshold_points` 不超过积分的最高门槛，同门槛取最小 `member_level_id`。支付后、实扣前退款时，流水改为 `VOIDED`。

## 6. 过程与跨域事务边界

| 过程 | 调用主体 | 主要写入/状态 | 外部接口 |
| --- | --- | --- | --- |
| `sp_create_order @customer_id, @fulfillment_method, @order_no, @items_json, @ordered_at = NULL` | 收银员 | 订单、明细、价格快照、`PENDING_PAYMENT` | A 定价函数；C `sp_lock_order_inventory`。 |
| `sp_pay_order ...` | 收银员 | 支付、`PAID`、待生效积分 | 无直接跨表更新顾客。 |
| `sp_start_production @order_id` | 厨师 | `PAID → IN_PRODUCTION` | 无。 |
| `sp_finish_production @order_id` | 配餐员 | 实扣后转待取/待配送，创建配送记录 | C `sp_consume_order_inventory`。 |
| `sp_pick_up_order @order_id` | 配餐员 | `READY_FOR_PICKUP → PICKED_UP`、积分生效 | A `sp_apply_customer_points`。 |
| `sp_pick_up_delivery ...` / `sp_confirm_delivery ...` | 骑手 | 配送/订单终态、积分生效 | A 积分接口。 |
| `sp_cancel_or_refund_order @order_id, @reason, @operator_employee_id` | 店长 | 取消/全额退款、流水作废 | C `sp_release_order_inventory`、`sp_write_audit_log`。 |

所有上述写过程以 `USER_NAME()` 解析并验证 C 的活跃员工和岗位；每个 B 外层事务覆盖本域写入与跨域调用。库存永远由 C 过程维护，顾客积分和等级永远由 A 过程维护。

## 7. 验收夹具的受限例外

生产流程中，B 不直接写 `Product` 或 `Customer`。但当前冻结计划没有提供 A 的 `sp_create_product`、`sp_update_product_price` 或测试会员积分夹具过程签名。为使 B 的验收可构造“停用商品”“无 BOM 商品”、历史价格快照和确定性会员升级反例，`10b_order_acceptance_tests.sql` 只允许部署主体在每个外层事务中临时写入/更新 `Product`、`Customer.current_points`；所有此类 DML 都随测试 `ROLLBACK` 清除，且不在 `EXECUTE AS USER = 'test_*'` 业务主体下运行。订单、明细、支付和积分流水仍绝不直接插入或更新。
