# ER 图符号图例（legend）

> 属主：成员 C（计划 §7.1）。适用于第二阶段全部 ER 图（三份域子图 + 合并总图）。统一采用**乌鸦脚（Crow's Foot）**表示法；源文件为 draw.io（`.drawio`），导出 `.svg`。命名约定（实体名、属性名）由 A 在 `docs/stage2/naming.md` 统一核对，图内实体名一律与表名逐字一致、属性名与数据字典逐字一致。

## 1. 实体与属性

- **矩形 = 实体**（对应一张表）；标题行为实体名（= 表名）。
- 实体内逐行列出属性，前缀标注：
  - `PK` 主标识（主码组成部分）；
  - `UK` 候选标识（唯一键 / 唯一索引）；
  - `FK` 外码；
  - `PKFK` 主码兼外码（如 `Inventory.ingredient_id`）。
- **独立实体 vs 关联实体**：M:N 联系用**关联实体**（独立矩形，如 `ProductBom`、`ComboComponent`、`EmployeeBusinessRole`），不直接以一条线画 M:N。
- **1:1 共享标识**：`Inventory` 的 `ingredient_id` 既是 PK 又是 FK（对 `Ingredient`），画为标识性联系、子端标 `PKFK`。
- **跨域实体**：非本域但参与联系的实体用**灰色矩形**，只列参与本图联系所需的键列与少量判别列（如 C 子图中的 `Ingredient`、`Delivery`）。
- 触发器等数据库中不存在的机制一律不画；图只反映 v0.1 实际对象（以活库目录为准）。

## 2. 联系、基数与参与约束

每条联系 = 一段连线，**两端各标一个符号**：

- **某端的符号描述「对端每条记录对应本端多少条记录」**（符号贴近哪一端，就描述那一端；鸦爪恒在"多"端）。例：`Inventory → InventoryMovement` 的 `1:N`——`Inventory` 端画单竖线（每条流水对应恰好一条库存行），`InventoryMovement` 端画圈加鸦爪（每条库存行对应零或多条流水）。**2026-10-17 订正**：本条原写作"近实体端的符号描述本实体侧每条记录对应多少个对端"，方向与实际画法相反（OI-07，A 发现）；四种端点符号与三张图的端点均未变，只改措辞。
- **最小基数**：圈（`o`） = 可选的 0；无圈 = 必须 ≥ 1。
- **最大基数**：竖线 = 至多 1；鸦爪 = 多。

四种端点符号（写作"竖线 / 鸦爪 / 圈"的组合；draw.io 箭头样式名一并给出）：

- **恰好 1**：单竖线 —— draw.io 样式 `ERone`。
- **零或 1**：圈加竖线 —— draw.io 样式 `ERzeroToOne`。
- **一或多**：竖线加鸦爪 —— draw.io 样式 `ERoneToMany`。
- **零或多**：圈加鸦爪 —— draw.io 样式 `ERzeroToMany`。

补充约定：

- **外码可空性决定被引用端（主表端）的符号**：可空外码（如 `Delivery.rider_employee_id`）→ 被引用端为「圈加竖线」（0..1）；非空外码 → 被引用端为「单竖线」（恰好 1）。
- **外码所在端（从表端）的最大基数按结构判定**：外码列恰好构成从表主码、或受**全量唯一约束**（唯一约束 / 唯一索引）时为「圈加竖线」（0..1，如 `Inventory.ingredient_id` 的 PKFK、`Payment.order_id` 的 `UQ_Payment_order_id`）；**过滤唯一索引只在其过滤条件内唯一，不把最大基数压到 1**（如 `UQ_ProductCategory_is_primary`、`UQ_ReplenishmentSuggestion_ingredient_id`、`UQ_SalesOrder_pickup_code`）；否则为「圈加鸦爪」（0..N）。本库没有任何结构约束要求"父项至少有一个子项"。
- **端点只表达 DDL 结构基数**（2026-10-24 B 在 `business-rule-mapping.md` 作为基数口径负责人冻结，OI-09 收口）：业务上必需而结构不保证的约束（如"成功订单至少 1 条售卖项""过程保证恰好 1 条明细"）**不改变端点符号**，写进联系标签并在 `business-rule-mapping.md` 写明实现机制（约束 / 过程 / 人工检查）。
- **OI-09 收口（2026-10-27，C）**：原「参与约束按业务规则判定」口径已废止，三张子图与合并总图统一按结构口径；C 子图 r6（`PurchaseOrder → PurchaseOrderItem`）从端已由 `ERoneToMany` 改为 `ERzeroToMany`，"业务恰好 1 条（过程保证）"留在标签。
- 联系的文字标签：域子图用 `两端基数（结构口径）— 实现机制/业务说明`，例：`1:1 — FK 唯一（PKFK）；业务上原料可暂无库存行`；合并总图统一用 `BR-xx` 指向 `business-rule-mapping.md`，结构不保证的业务附加集中列在图例。

## 3. 画法与合并约定

1. 一对一 / 一对多：主表端在"一"侧、从表端在"多"侧，连线从"一"指向"多"或反向均可，以两端符号为准。
2. 同一实体在多张图出现时保持同名同键列；总图合并（C）以各域子图为准，不改写域内实体内容，去重实体、保留全部联系。总图 `docs/er/stage2-model.drawio` / `.svg` 由 `sql/01–03`（含 `03`/`05` 唯一约束）同源生成：逐表列全列（属性名与子图一致）、25 实体 / 35 条物理外键、联系标签用 BR 编号；域子图继续保留各自的灰色跨域实体画法。
3. 联系跨图出现（如 `Delivery → EmployeeAccount`）时，在两图各自画全本地一端，总图合并为一条。
4. 图例变更（新增符号或约定）由 C 更新本文件，并在 `docs/stage2/open-issues.md` 登记影响范围。
