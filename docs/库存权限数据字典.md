## 1. `Inventory` — 原料库存

**作用：** 每种原料一行，保存**账面量（现有量）**与**锁定量**两个实字段。下单锁库只增加锁定量、不动现有量，可售量随之减少，这是防超卖的核心（《业务流程》第 2 步）。原料主档（单位、安全库存线）在 A 的 `Ingredient`，本表只存数量；两表通过 `ingredient_id` 一一对应。

| 字段 | 中文含义 | 数据类型 | 可空 | 默认值 | 主 / 外键 | 取值范围 | 来源文档段落 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| `ingredient_id` | 原料代理主键；同时是指向 A 域 `Ingredient` 的外键 | `BIGINT` | 否（主键兼外键） | 无 | `PK_Inventory`；`FK_Inventory_Ingredient` → `Ingredient(ingredient_id)` | — | 计划 §2.1（`Inventory` 主键与关键字段）；《数据边界清单》2.1 库存与补货域「库存表」 |
| `on_hand_qty` | 账面量 / 现有量：物理在库数量 | `DECIMAL(12,3)` | 否 | 无 | — | `>= 0`（`CK_Inventory_on_hand_qty`） | 《数据边界清单》术语表；2.1 库存与补货域「库存表（账面/现有量 + 锁定量）」 |
| `locked_qty` | 锁定量：被未完成订单占用的数量 | `DECIMAL(12,3)` | 否 | 无 | — | `>= 0`（`CK_Inventory_locked_qty`） | 《业务流程》2（下单锁库）；《数据边界清单》术语表 |
| `updated_at` | 最近一次数量变更时间 | `DATETIME2(0)` | 否 | 无 | — | 无约束 | 计划 §2.1（`Inventory` 关键字段） |

**约束与索引：** 主键 `PK_Inventory`（`ingredient_id`）；外键 `FK_Inventory_Ingredient`；无其他索引。主键即外键，故**不存在没有原料主档的库存行**。

**设计要点：**
- **可售量不落库**：`available_qty = on_hand_qty - locked_qty` 只在 `v_inventory_available` 中计算（计划 全局约束），避免冗余字段与两个实字段不一致。
- **不设 `locked_qty <= on_hand_qty` 的约束**：`sp_adjust_inventory`（盘盈/盘亏）只改现有量、不动锁定量，合法操作可能使现有量暂时低于锁定量（如盘亏），若加大小关系约束会把这类调整一并挡掉。可售量非负由 `sp_lock_order_inventory` 在锁库时以 `UPDLOCK, HOLDLOCK` 校验（计划 §2.3 line 142）。
- **没有库存行的原料**：视图按 `0/0/0` 显示并判低库存，但 `sp_refresh_replenishment_suggestion` 直接 `RETURN`，不产生建议——避免对未建账原料提出无意义的补货单。
- 两个数量的变化全部经过程写入（锁库 `+locked`、释放 `-locked`、实扣 `-on_hand`/`-locked`、收货 `+on_hand`、调整 `±on_hand`），业务角色被 `DENY` 直接 `UPDATE`（计划 §5 C-2）。

## 2. `InventoryMovement` — 库存变动流水

**作用：** 每一次库存数量变化一行，是账实勾稽与第三阶段补货预测的唯一数据源（《数据边界清单》2.1「库存变动流水……第3阶段做补货预测没有流水寸步难行」）。五种流水的数值语义由计划 §2.3 line 143 冻结，`CHECK` 只约束取值与“不能两个方向都为 0”，**形状（哪一类该动哪个方向）由过程保证**。

| 字段 | 中文含义 | 数据类型 | 可空 | 默认值 | 主 / 外键 | 取值范围 | 来源文档段落 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| `inventory_movement_id` | 流水代理主键 | `BIGINT IDENTITY(1,1)` | 否（主键） | 自增 | `PK_InventoryMovement` | — | 计划 §2.1；《数据边界清单》2.1 库存与补货域「库存变动流水」 |
| `ingredient_id` | 变动原料 | `BIGINT` | 否 | 无 | `FK_InventoryMovement_Inventory` → `Inventory(ingredient_id)` | — | 同上 |
| `movement_type` | 流水类型 | `VARCHAR(20)` | 否 | 无 | — | `LOCK` / `RELEASE` / `CONSUME` / `RECEIPT` / `ADJUSTMENT`（`CK_InventoryMovement_movement_type`） | 计划 §2.1、§2.3 line 143 |
| `on_hand_delta` | 账面量变化量（带符号） | `DECIMAL(12,3)` | 否 | 无 | — | 与 `locked_delta` 至少一个非 0（`CK_InventoryMovement_delta_not_zero`） | 计划 §2.3 line 143 |
| `locked_delta` | 锁定量变化量（带符号） | `DECIMAL(12,3)` | 否 | 无 | — | 同上 | 计划 §2.3 line 143 |
| `reference_type` | 关联单据类型 | `VARCHAR(20)` | 否 | 无 | — | `ORDER` / `PURCHASE_ORDER` / `ADJUSTMENT`（`CK_InventoryMovement_reference_type`） | 计划 §2.3 |
| `reference_id` | 关联单据 ID：订单 ID 或采购单 ID | `BIGINT` | 是（见约束） | 无 | 无外键（多态引用） | `reference_type` 为 `ORDER`/`PURCHASE_ORDER` 时必须非空，为 `ADJUSTMENT` 时必须为空（`CK_InventoryMovement_reference`） | 计划 §2.3 line 142、§2.1 |
| `moved_at` | 变动时间 | `DATETIME2(0)` | 否 | 无 | — | 无约束 | 计划 §2.1 |

**约束与索引：** 主键 `PK_InventoryMovement`；外键 `FK_InventoryMovement_Inventory`（→ `Inventory`，**不是** `Ingredient`，故没有库存行的原料写不出流水）；无其他索引。

**五类流水的数值语义（计划 §2.3 line 143 冻结，过程必须逐条遵守）：**

| 类型 | `on_hand_delta` | `locked_delta` | `reference_type` / `reference_id` | 写入过程 |
| --- | --- | --- | --- | --- |
| `LOCK` | `0` | `+需求量` | `ORDER` / 订单 ID | `sp_lock_order_inventory` |
| `RELEASE` | `0` | `-释放量` | `ORDER` / 订单 ID | `sp_release_order_inventory` |
| `CONSUME` | `-实扣量` | `-实扣量` | `ORDER` / 订单 ID | `sp_consume_order_inventory` |
| `RECEIPT` | `+收货量` | `0` | `PURCHASE_ORDER` / 采购单 ID | `sp_receive_inventory`（待签名定案后实现，见 §12） |
| `ADJUSTMENT` | `±调整量`（非 0） | `0` | `ADJUSTMENT` / `NULL` | `sp_adjust_inventory` |

**设计要点：**
- **一笔流水一行，不合并**：同一原料被同一订单的多条商品行共用时，锁库先按原料汇总需求量，再用一条按原料分组的 `INSERT ... SELECT` 只写一条 `LOCK`，因此“订单 ID + 原料 + 类型”在一张订单内唯一，`v_order_inventory_trace` 可直接按流水回溯。
- **`reference_id` 故意不建外键**：它按 `reference_type` 分别指向 B 的 `SalesOrder` 或本域 `PurchaseOrder`，是典型多态引用；用 `CHECK` 保证“单据类流水必须有单号、人工调整必须没有单号”。
- **账实勾稽不变量**：对任一原料，`Inventory.locked_qty` 恒等于该原料全部流水的 `SUM(locked_delta)`；对任一订单，`LOCK`/`RELEASE`/`CONSUME` 三类流水的 `locked_delta` 之和等于该订单当前占用的锁定量。这两条是 `10c` 的核心断言（计划 §5 C-3）。
- `ADJUSTMENT` 必须同时写审计日志（计划 §2.4），`LOCK`/`CONSUME` 由订单状态机保证，`RELEASE` 在能解析出员工时补记审计。

## 3. `ReplenishmentSuggestion` — 补货建议单

**作用：** 记录“某原料低于安全库存线、建议补多少”。两个来源：实扣后自动生成/更新（`sp_consume_order_inventory` → `sp_refresh_replenishment_suggestion`），以及值班经理手工创建（`sp_create_replenishment_suggestion`）。**开放态过滤唯一索引**保证每种原料最多只有一张开放建议（《业务流程》7 的“一张待审核建议”）。

| 字段 | 中文含义 | 数据类型 | 可空 | 默认值 | 主 / 外键 | 取值范围 | 来源文档段落 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| `replenishment_suggestion_id` | 建议单代理主键 | `BIGINT IDENTITY(1,1)` | 否（主键） | 自增 | `PK_ReplenishmentSuggestion` | — | 计划 §2.1；《数据边界清单》2.1「补货建议单」 |
| `ingredient_id` | 建议补货的原料 | `BIGINT` | 否 | 无 | `FK_ReplenishmentSuggestion_Ingredient` → `Ingredient(ingredient_id)`；同时受过滤唯一索引约束 | — | 同上；《业务流程》7 |
| `current_qty` | 生成/更新建议时的现有量快照 | `DECIMAL(12,3)` | 否 | 无 | — | 无约束 | 计划 §5 C-1（以实扣后的 `on_hand_qty` 写入） |
| `suggested_qty` | 建议补货量 = 安全库存线 − 触发时现有量（保留 3 位小数，刚好补到安全线） | `DECIMAL(12,3)` | 否 | 无 | — | `> 0`（`CK_ReplenishmentSuggestion_suggested_qty`） | 计划 §2.1、§5 C-1；《业务流程》7 |
| `suggestion_status` | 建议单状态 | `VARCHAR(20)` | 否 | 无 | — | `PENDING` / `SUBMITTED` / `APPROVED` / `REJECTED` / `CLOSED`（`CK_ReplenishmentSuggestion_suggestion_status`） | 计划 §2.1、§5 C-1 |
| `created_by_employee_id` | 建议创建人；自动生成时为触发实扣的员工 | `BIGINT` | 否 | 无 | `FK_ReplenishmentSuggestion_CreatedByEmployee` → `EmployeeAccount(employee_id)` | — | 计划 §2.1、§5 C-1（自动建议创建人取触发实扣的当前员工） |
| `submitted_by_employee_id` | 提交人 | `BIGINT` | 是 | 无 | `FK_ReplenishmentSuggestion_SubmittedByEmployee` → `EmployeeAccount(employee_id)` | 提交前为空 | 计划 §2.1、§5 C-1 |
| `approved_by_employee_id` | 审批人 | `BIGINT` | 是 | 无 | `FK_ReplenishmentSuggestion_ApprovedByEmployee` → `EmployeeAccount(employee_id)` | 审批前为空 | 同上 |
| `rejected_by_employee_id` | 驳回人 | `BIGINT` | 是 | 无 | `FK_ReplenishmentSuggestion_RejectedByEmployee` → `EmployeeAccount(employee_id)` | 驳回前为空 | 同上 |

**约束与索引：**
- 主键 `PK_ReplenishmentSuggestion`；4 个指向 `EmployeeAccount` 的外键；1 个指向 `Ingredient` 的外键。
- 过滤唯一索引 `UQ_ReplenishmentSuggestion_ingredient_id`：`ON (ingredient_id) WHERE suggestion_status IN ('PENDING', 'SUBMITTED', 'APPROVED')`——**开放态的唯一定义**。`REJECTED` 与 `CLOSED` 不在索引内，因此同一原料可以留下任意多条历史建议，但只要有一张未结案的就插不进第二张。

**状态迁移（全部经过程，禁止直接 `UPDATE`）：**

| 迁移 | 触发过程 | 同时写入 |
| --- | --- | --- |
| （新建）→ `PENDING` | `sp_refresh_...`（自动）/ `sp_create_...`（手工） | `current_qty`、`suggested_qty`、`created_by_employee_id`；审计 `CREATE_...` |
| `PENDING` → `PENDING`（更新量） | `sp_refresh_...` / `sp_update_...` | 刷新时更新 `current_qty`+`suggested_qty` 且**不改创建人**；手工调整只改 `suggested_qty`；审计 `UPDATE_...` |
| `PENDING` → `SUBMITTED` | `sp_submit_...`（值班经理） | `submitted_by_employee_id`；审计 `SUBMIT_...` |
| `SUBMITTED` → `APPROVED` | `sp_approve_...`（店长） | `approved_by_employee_id`，同一事务生成 `PurchaseOrder` + 明细；审计 `APPROVE_...` |
| `SUBMITTED` → `REJECTED` | `sp_reject_...`（店长） | `rejected_by_employee_id`、`@reason`；审计 `REJECT_...` |
| `PENDING`/`SUBMITTED` → `CLOSED` | `sp_refresh_...`（现有量回到安全线以上）/ `sp_receive_inventory`（关联采购单收齐） | 无员工字段 |

**设计要点：**
- **已有 `APPROVED` 建议时不新增、不修改**：`sp_refresh_replenishment_suggestion` 在该分支静默跳过，等关联采购单收齐关单把建议置 `CLOSED` 后，下次实扣才会重新开单——避免审批中的建议被实扣反复改写。
- `current_qty` 是**快照**而非实时值：看板视图展示的是开单/更新那一刻的现有量，实时现有量从 `v_inventory_available` 取。
- 本表不设 `created_at`：创建时间可由同事务的 `AuditLog.logged_at` 取得，避免两处时间戳不一致。

| `replenishment_suggestion_id` | 来源建议单 | `BIGINT` | 否 | 无 | `FK_PurchaseOrder_ReplenishmentSuggestion` → `ReplenishmentSuggestion(replenishment_suggestion_id)` | — | 计划 §2.1、§5 C-1 |
| `purchase_status` | 采购单状态 | `VARCHAR(20)` | 否 | 无 | — | `DRAFT` / `APPROVED` / `PARTIALLY_RECEIVED` / `CLOSED`（`CK_PurchaseOrder_purchase_status`） | 计划 §2.1、§2.3 line 146 |
| `approved_by_employee_id` | 审批店长 | `BIGINT` | 是 | 无 | `FK_PurchaseOrder_ApprovedByEmployee` → `EmployeeAccount(employee_id)` | 审批前为空 | 计划 §2.1、§5 C-1 |
| `approved_at` | 审批时间 | `DATETIME2(0)` | 是 | 无 | — | 审批前为空 | 计划 §2.1、§5 C-1 |

**约束与索引：** 主键 `PK_PurchaseOrder`；唯一键 `UQ_PurchaseOrder_purchase_order_no`；外键 `FK_PurchaseOrder_ReplenishmentSuggestion`、`FK_PurchaseOrder_ApprovedByEmployee`。

**设计要点：**
- **单号生成**：`'PO' + CONVERT(VARCHAR(8), SYSDATETIME(), 112) + 当日 4 位序号`，序号取当日已有单号的最大值 +1（`WITH (UPDLOCK, HOLDLOCK)` 防并发重号），并由唯一键兜底（计划 §5 C-1）。
- **`DRAFT` 在第一阶段不会被产生**：`sp_approve_replenishment_suggestion` 在审批事务内直接写入 `APPROVED`。该状态值由计划 §2.1 冻结在 `CHECK` 中，为后续“先建单后审批”的流程预留。
- **两列可空的原因**：`approved_by_employee_id`、`approved_at` 可空是为了兼容 `DRAFT` 这一预留状态；经第一阶段唯一路径（审批生成）产生的行，两列必有值。
- **数据库未强制“一张建议单最多一张采购单”**：过程侧由“只有 `SUBMITTED` 可审批”+“已有 `APPROVED` 建议时不再新增”共同保证。当前实现下该唯一性成立，但约束层没有兜底。
- 收货由 `sp_receive_inventory` 累计 `PurchaseOrderItem.received_qty`：未收齐转 `PARTIALLY_RECEIVED`，收齐转 `CLOSED` 并把来源建议置 `CLOSED`（计划 §2.3 line 146）。

## 5. `PurchaseOrderItem` — 采购单明细

**作用：** 采购单的原料与数量明细。第一阶段审批只生成一条（一张建议单只对应一个原料），但主键设计为复合键以兼容后续多明细采购单；收货进度落在 `received_qty`。

| 字段 | 中文含义 | 数据类型 | 可空 | 默认值 | 主 / 外键 | 取值范围 | 来源文档段落 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| `purchase_order_id` | 所属采购单 | `BIGINT` | 否（复合主键） | 无 | `PK_PurchaseOrderItem`；`FK_PurchaseOrderItem_PurchaseOrder` → `PurchaseOrder(purchase_order_id)` | — | 计划 §2.1 |

| `ordered_qty` | 订购量（审批时取建议量） | `DECIMAL(12,3)` | 否 | 无 | — | `> 0`（`CK_PurchaseOrderItem_ordered_qty`） | 计划 §2.1、§5 C-1 |
| `received_qty` | 已收货量（多次收货累计） | `DECIMAL(12,3)` | 否 | `0`（`DF_PurchaseOrderItem_received_qty`） | — | `>= 0` 且 `<= ordered_qty`（`CK_PurchaseOrderItem_received_qty`） | 计划 §2.1、§2.3 line 146 |

## 11. 权限模型小结

```
EmployeeAccount ──(EmployeeBusinessRole)── BusinessRole ──(RolePermission)── 过程/视图名
        │                                        │                                │
   database_user_name == USER_NAME()       role_code == 'role_' + code       08 的 GRANT EXECUTE/SELECT
```

- **解析链**：登录主体 → `EmployeeAccount.database_user_name = USER_NAME()` → 必须为 `ACTIVE` → 过程内校验传入的员工 ID 等于解析结果（计划 全局约束）。
- **授权链**：`BusinessRole.role_code` → 同名数据库角色 `role_*` → `RolePermission` 白名单里的过程/视图 `GRANT EXECUTE`/`GRANT SELECT`（`08_roles_permissions.sql`，计划 §5 C-2）。
- **成员关系链**：`sp_assign_employee_business_role` 同时写 `EmployeeBusinessRole` 与 `ALTER ROLE ... ADD MEMBER`；`sp_revoke_...` 同时删映射与 `DROP MEMBER`；停用员工撤销全部成员关系。
- **角色同步的最小权限**：三个角色同步过程（`sp_assign_...`、`sp_revoke_...`、`sp_update_employee_status`）不以 `EXECUTE AS OWNER` 提权，而是由 `08` 创建的证书用户签名获得 `ALTER ANY ROLE`/`ALTER ANY USER`；普通店长只有这三个过程的 `EXECUTE`（计划 §5 C-1）。
- **测试主体**：`08` 创建不带登录的 `test_*` 用户，`09c` 为其插入 `EmployeeAccount` 行，再由 `test_store_manager` 通过 `sp_assign_employee_business_role` 分配业务角色；验收脚本一律 `EXECUTE AS USER = '<test_主体>'` + `REVERT`（计划 §5 C-2/C-3）。
- **授权规模（`08` 实机核对）**：`CK_RolePermission_permission_code` 白名单共 **46 项**（36 个过程 + 10 个视图）；`08` 共 **52 条 `GRANT`**（店长 25 过程 + 10 视图，值班经理 4 过程 + 4 视图，其余岗位合计 9 条），覆盖全部 46 个对象。C 域贡献 10 个过程（`sp_adjust_inventory`、5 个补货过程、3 个角色同步过程、`sp_receive_inventory`）与 4 个视图。
- **不经白名单的对象**：`sp_write_audit_log`、`sp_refresh_replenishment_suggestion`、`sp_lock_order_inventory`/`sp_release_...`/`sp_consume_...` 只由其他过程经 `dbo` 所有权链调用，**不向任何业务角色 `GRANT EXECUTE`**——它们不是岗位的操作入口，暴露出去只会扩大攻击面（计划 §2.4、§5 C-1）。
- **禁止直改敏感字段（计划 §5 C-2 line 315）**：7 个业务角色一律 `DENY UPDATE`：表级 `dbo.Inventory`、列级 `dbo.SalesOrderItem(unit_price)`、列级 `dbo.Customer(current_points)`，共 21 行权限记录。`DENY` 优先于任何 `GRANT`，且列级 `DENY` 优先于表级 `GRANT`；库存与积分的写入只能经过程（`dbo` 所有权链不受 `DENY` 影响，已实机验证 `sp_adjust_inventory` 仍可改 `on_hand_qty`）。
- **矩阵按字面实施**：计划 §5 C-2 line 314 未把补货的“创建/调整/提交”和“采购收货”授予店长，故店长**不能**自己创建补货建议、也不能执行收货（收货是值班经理的入口，审批归店长，形成职责分离）；同理“库存/补货视图”我按字面理解为 C 域全部四个视图（含 `v_order_inventory_trace`）。若项目组本意是把收货一并交给店长，只需删除 `08` 中对应的一行 `GRANT`（已记入计划 §8 变更记录 2026-09-24 待确认）。

`EmployeeBusinessRole` 与 `ALTER ROLE` 的同步过程**不使用 `EXECUTE AS OWNER`**（否则 `USER_NAME()` 会指向 `dbo`），改为由 `08` 的证书签名取得 `ALTER ANY ROLE`/`ALTER ANY USER`，见 §11。三个过程都只接受白名单里的 `BusinessRole.role_code`（固定 7 个岗位），动态角色名由 `role_` + `role_code` 拼出，过程本身不创建服务器登录名。

**事务纪律：** 每个过程都以 `SET XACT_ABORT ON` + 显式事务实现，四个订单库存过程支持嵌套调用（`@@TRANCOUNT = 0` 才自行提交），失败即回滚整个外层事务——保存点在 `XACT_ABORT ON` 下不可用，冲突已记入计划 §8 变更记录（2026-09-24）。三个角色同步过程同样在显式事务内执行，`ALTER ROLE` 的成员变更可随事务回滚（已实机验证）。

**待定项：** `sp_receive_inventory` 的签名（是否补第 3 参数 `@received_qty DECIMAL(12,3)`）已记入计划 §8 变更记录 2026-09-24 待 B 定夺；§12 表格中的这一行随签名定案后同步更新。
