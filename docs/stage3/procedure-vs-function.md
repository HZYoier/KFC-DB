# 第三阶段：过程、函数与查询各做什么

订单下单是一个写入动作，折扣是一个计算结果，销售报表是一次带校验的查询。这里把三件事分开，页面只提交参数或展示数据库结果。

| 对象 | 类型 | 为什么放在这一层 |
| --- | --- | --- |
| `sp_create_order` / `sp_customer_place_order` | 写存储过程（B） | 生成订单、保存售价和折扣、调用库存锁定。所有写入必须同一个事务成功，库存不足时整单回滚。 |
| `fn_calculate_discount` | 内联表值函数（A） | 按顾客和毛额返回一行折扣率与折扣额，不写订单；两种下单方式都用同一个规则。 |
| `v_settled_sales_line` | 视图（B） | 把已完成的自取和外送统一成销售明细，只计售卖项。所有报表看到的状态、数量和净额一致。 |
| `sp_sales_report` | 只读存储过程（B） | 校验日期，可抛出明确错误，一次返回总计和商品明细两份结果。没卖出商品时总计仍有一行 0。 |
| `fn_product_sales_summary` | 内联表值函数（A） | 读取同一视图，按商品返回销售汇总，可与其他查询连接或再聚合。日期无效时返回空结果，不写表。 |
| `sp_adjust_inventory` / `fn_replenishment_qty` | 写过程 / 计算函数（C） | 前者检查身份和库存后写入数量与流水；后者只按可售量和目标量给出建议数，不自动补货。 |

支付读取订单已经保存的折后总额。配餐仍按照原始明细数量制作，套餐组件不参与收入或折扣分摊。分币尾差优先给毛额最大的一行，同额时先用明细 ID 小的一行。若这一行会超过毛额或扣成负数，就沿同一顺序用下一行余额。例如五件各 0.10 元的商品若共优惠 0.03 元，分摊后恰好三行各优惠 0.01 元。

完成订单时按本单锁定的原料核对实扣记录。下单后修改商品 BOM 不影响旧单的出库范围。如果订单没有锁库流水，仍要核对现有 BOM 对应的实扣；没有 BOM 的商品跳过这项检查。

## 运行与验证

从仓库根目录运行 B 的真库测试：

```powershell
.venv\Scripts\python.exe -X utf8 tests/stage3/b_programmability/run_b_stage3.py --sql-server 'localhost\MSSQLSERVER2'
```

过程、触发器和窗口查询共用一次隔离库部署。测试比对两种下单方式的折扣和总额、视图与 A 函数的统计结果，并验证订单完成触发器的单行与多行行为。终端证据见 [B 联调记录](../../result/stage3/b-13b-21b-22b-23b.txt)。

`23b_window_queries.sql` 每个有销售的日期只有一行。先计算每日折后销售额，再按 `sale_date` 从第一天累加到当前行；没有销售的日期不补行。增加累计列不会改变每日聚合的行数。

当前验证顺序是 `20 → 21b → 21a → 21c → 22b → 22c`。旧版 38 条 SQL 回归在安装域对象前后各通过一遍，两遍都使用 v1.0 权限。正式 v1.1 迁移仍需 C 的 `27_permissions.sql`。

订单页面现有接口可显示折后总额，单独展示折扣率与金额仍需授权后的明细读取接口。B 的报表过程可处理结束日期 `9999-12-31`，A 的汇总函数还需处理这一输入，避免将日期加一天时溢出。
