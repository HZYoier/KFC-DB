# 第二阶段三人协作实施计划

**Goal:** 回头审查第一阶段的 v0.1 关系设计是否合理。用 ER 模型说明实体、属性、联系、基数和参与约束，用函数依赖与规范化论证现有结构的取舍，用迁移脚本修正确有问题的部分，再把数据库封装成按角色可操作的应用。

**Architecture:** 沿用第一阶段的三条业务线——A 主数据与定价、B 订单与履约、C 库存权限与集成。第二阶段不改这条线，改的是"从库到应用"的层次：库结构先经一次受控迁移升到 v1.0，再由统一的访问层封装，最后按岗位暴露操作界面。

**Spec:** 教学安排《第二阶段 · 第 5—9 周 数据设计、重构与应用开发》，含第五周（ER 模型）与第六周（函数依赖与规范化）两份讲解。库内依据为[业务流程](业务流程.md)、[数据边界清单](数据边界清单.md)、[角色与职能清单](角色与职能清单.md)与三份数据字典。

教学材料原文尚未归档到本仓库；本文对教学安排的转述暂作需求输入，不能代替逐项核对原文。C 在 2.1 结束前补充原文来源或允许归档的摘录、要求编号与本文交付物的对应表，记录于 `docs/stage2/source-requirements.md`；未核对的要求明确标记，不记为已通过。

## 0. 阶段目标与三个子阶段

第二阶段按内容分成三个子阶段。作业的周次安排与它们一一对应，但本计划的推进、验收和分工一律按子阶段走，不按周次切分——一个子阶段里的产物归一个人负责到底，避免每周换手。

| 子阶段 | 目标 | 主要产出 |
| --- | --- | --- |
| 2.1 ER 模型重建 | 从 v0.1 反推 ER 模型，核对实体、联系、基数和参与约束，形成 v0.1 问题清单 | ER 图（可编辑源 + 导出图）、业务规则与映射清单、v0.1 问题清单、设计说明与验证记录 |
| 2.2 规范化与迁移 | 识别更新异常与函数依赖，判断范式，完成反规范化取舍与迁移设计 | 依赖与范式分析、重构方案、三份域迁移脚本、`run_migration.sql`、`regression.sql` 与回归结果 |
| 2.3 应用开发 | 实现访问层与核心业务接口，做成按角色可操作的应用 | 连接配置、DAO/API、登录与 CRUD 界面、角色界面、集成测试与操作手册 |

本计划用两个版本号指代库结构的两个状态：**v0.1** 是第一阶段的交付（25 张表、51 条 `CHECK`、35 条外键，由 `sql/run_all.sql` 从空库一次建出），**v1.0** 是迁移完成后的结构。2.2 负责从前者过渡到后者，2.3 的应用一律面向 v1.0。

v0.1 的源码基线固定为提交 `b557d4997d1b48d3cc15ed8be3cfa78102a626df` 中的 `sql/`，域验收基线为 A 13、B 15、C 18 条。C 在迁移预检中核对基线对象清单与定义摘要，不能仅按表数量识别版本。第一阶段 `00`—`10c` 和 `run_all.sql` 保留为 v0.1 复现路径；v1.0 的对象变更通过新增迁移文件实施。版本管理与回归辅助表另列清单，不与业务表数量混算。

子阶段之间有依赖：2.2 的迁移依据是 2.1 的问题清单，2.3 的界面依据是 2.2 定稿的库结构。上游没定稿就动下游，返工量会大于等待成本。

## 1. 第二阶段新增的全局约束

第一阶段的全局约束继续有效，另有几条从本阶段开始生效：

- **第 6 周起不再删库重建。** 教学安排写明：删库重建会丢失已有数据，不能代替迁移；迁移前必须先备份或复制数据库。第一阶段的 `00_create_database.sql` 检测到同名库会主动 `THROW` 停下，这条保护现在正好用得上，不要为了跑迁移去删库。
- **迁移脚本不得删除已有业务数据。** 拆表、合表、改字段都要能带着基线数据走完，并且保留迁移前的结果快照供逐项比对。
- **README、数据字典、ER 图三处随改随更。** 迁移改了结构而文档没跟，第二阶段末会比第一阶段更难对账。
- **应用的业务值一律参数绑定**，禁止把用户输入拼入 SQL；过程名、排序列等不能绑定的标识符只从静态白名单选择。数据库中现有的角色同步动态 SQL 可保留其固定白名单与 `QUOTENAME` 保护，不以“全文没有字符串拼接”作为验收判据。
- **连接凭据不入仓。** 员工连接使用登录框输入或个人 Windows 集成认证；部署秘密从本机环境或安全交互提供，沿用第一阶段“库中不留明文口令”的口径。
- 第一阶段关于 `unit_price` / `promotion_id` 必须是成交快照的约定不变，第二阶段的应用层不得绕过它反算历史订单。

## 2. v0.1 问题清单

第 5 周的正式交付物之一。这里先落五条已核实的问题（三条保留项、两条待处理项），其余在第 5 周的实体与联系核对中补充。

### 2.1 已核实的保留项

**供应商实体不引入。** v0.1 的 SQL 架构没有供应商实体，`PurchaseOrder` 的 6 列（`purchase_order_id`、`purchase_order_no`、`replenishment_suggestion_id`、`purchase_status`、`approved_by_employee_id`、`approved_at`）里也没有 `supplier_id`，采购单发给了谁在库里无从回答。核对第一阶段业务流程后确认：从后台准备到补货闭环这条线上没有出现供应商选择、比价或到货评价，采购一律视为向门店唯一供应渠道补货。第二阶段默认不扩展该实体；C 核对教学原文后，若供应商是强制交付项须更新范围与本决定。日后按供应商统计进价与到货质量时再新增 `Supplier` 与采购外码，不把当前范围外功能伪装成已有约束问题。

**成交价与促销命中是历史事实快照，保留。** `SalesOrderItem.unit_price`、`promotion_id` 存的是下单那一刻算出的值。商品编号能决定商品当前基价，但决定不了历史成交价；把快照拆掉改成关联 `Product.base_price` 现算，改一次价就会改掉所有历史订单的金额。快照不因关联到商品就自动违反范式，是否存在反规范化必须依据本关系的候选码与函数依赖判断；订单总额等派生冗余另行分析。

**可售量不落列，保留。** `Inventory` 有主键兼外键 `ingredient_id`，以及 `on_hand_qty`、`locked_qty`、`updated_at`，共四列。可售量由现有量减锁定量得出，没有单独的可售量字段。派生值不物化，就不会出现“账面量改了、可售量忘了改”的不一致。

### 2.2 待处理项

**“每张订单至少有一条销售明细”由过程和权限保证，缺少独立的声明式约束。** 外码只能保证引用对象存在。现有 `sp_create_order` 在同一事务中先插主表，再插至少一条 `SELLABLE` 明细；岗位无基表写权限，所以正常业务入口已有保证，拥有高权限的直接写入仍能绕过。B 在 2.1 明确区分“业务必需”“DDL 已保证”“过程与授权保证”。禁止直接加一个在主表 INSERT 后立即要求已有明细的触发器，它会拒绝现有合法下单顺序。2.2 默认保留原子下单与禁止直接 DML，增加空明细输入、过程中断回滚和岗位直接插删明细被拒的回归；若要求覆盖 DBA 直写，B 必须先提出可执行的事务边界方案，验证合法建单再纳入迁移。

**`SalesOrder.total_amount` 与销售明细金额之和重复，需要给出口径。** v0.1 三笔种子订单的主表金额与销售明细 `SUM(unit_price × quantity)` 相等，当前是派生冗余而非独立金额口径；过程原子维护但缺少独立约束，直接改明细可能脱节。2.2 由 B 决定保留派生总额并说明实际用途与维护机制，或由冻结的销售明细求和、移除该列；不预设“冗余就必删”。

B 的分析必须以 `item_role = 'SELLABLE'` 的明细求和，并说明金额精度和舍入位置；当前没有订单级优惠，不能用尚未实现的优惠作为保留理由。保留时给出原子维护与一致性回归；删除时同时升级支付、退款、视图、跨域引用与基线比较，不能只删列。结论在 2.2 设计冻结时写入重构方案。

### 2.3 第 5 周补充

问题清单不止上面五条。第 5 周做实体与联系核对时，重点盯这几类：实体遗漏（某个业务对象没有对应表）、属性重复（同一事实存在两处）、联系表达不清（该用关联表的用了可空外码，或反之）、以及基数写错（因样例数据恰好一对一就认定业务上是一对一）。

## 3. 分工原则

**域主不变。** 第一阶段的分工按业务线划，第二阶段继续沿这条线：A 主数据、定价与会员，B 订单、支付与履约，C 库存、补货、权限与集成。理由很实际——ER 的实体、函数依赖的候选码、数据字典的属主都是按域走的，换人等于把别人的表重新读一遍，而第二阶段的三个子阶段都要用到这个域内知识。

**总集成归 C，专题汇总按主笔归属。** C 负责跨域协调、总 ER 图、迁移入口、回归汇总与权限集成；B 负责业务规则映射、重构方案和事务规范；A 负责命名规范、设计验证、访问层与手册。各域提交素材，由指定主笔汇总，不把所有跨域文档都默认交给 C。

**一个产物只有一个主人。** 合并类工作（总 ER 图、`regression.sql`）由 C 主笔，其余两人只提交自己域内的素材，不直接改合并后的文件，避免同一份文件两头改。

文件归属与交接格式以 §7.1 为准。本文问题清单由 C 维护；A/B 在域问题文件提出条目，C 合入本文，不由三人同时编辑第 2 节。

## 5. 子阶段 2.2：规范化与迁移

目标是在 v0.1 的副本上跑通一次受控迁移，证明迁移前后业务含义一致。

| 成员 | 负责范围 |
| --- | --- |
| A | 主数据域逐表：候选码 → 关键函数依赖 → 插入 / 修改 / 删除异常（各附一条数据例子）→ 1NF/2NF/3NF 判断 → 分解或保留理由；`11a_master_migration.sql`；更新主数据数据字典；**商品销售统计的迁移前基线** |
| B | 订单域同上；**重构方案主笔**，含无损连接与依赖保持分析；`11b_order_migration.sql`；更新订单履约数据字典；**订单明细的迁移前基线** |
| C | 库存权限域同上；`11c_inventory_security_migration.sql`；更新库存权限数据字典；**库存查询的迁移前基线**；**`run_migration.sql` 入口与 `regression.sql` 汇总** |

迁移脚本按域拆成三份再串一个入口，与第一阶段 `10a` / `10b` / `10c` 的写法保持一致。脚本内容按教学要求覆盖：新表创建、字段调整、主码候选码外码设置、必要的数据迁移、重复数据检查、旧表处理或保留说明。脚本之外还要配一份说明，写清四件事：执行顺序（三份脚本与入口的先后、与 `run_all.sql` 的关系）、数据冲突处理（遇到重复值或断链外码时是拒绝还是合并）、运行前提（实例上须已存在 v0.1、执行前须已备份）、以及失败恢复方法（在哪一步出错时如何退回到 v0.1）。回溯路径不写清楚，迁移一旦中途失败就只能删库重来，而这正是本阶段明令禁止的。

范式判断的几条口径要提前统一，免得三人各判各的：检查 2NF 要看所有候选码，不能只看主键；判断 3NF 要分析非平凡函数依赖的决定因素，不能只盯着主码；样例里没有重复值不等于依赖不成立；表不是越多越好，现有结构合理就保留并给出分析证据，需要演示异常时另建独立的关系示例，不要为了展示规范化而破坏原项目。一旦提出分解，须给出无损连接与依赖保持论证：前者证明连接不会丢失或引入伪元组，后者证明投影到各分表的依赖集合仍能推出原依赖，并非要求每条原依赖逐字出现在某一张分表。碰到某个域找不出异常，说明它如何避开异常，把“没有”也写成有依据的结论。

迁移前必须先备份或复制数据库。回归脚本要覆盖关键标识、关系映射、订单金额、商品销量、库存和角色权限，逐项记录迁移前基准、预期值、迁移后结果与差异解释。拆表带来的行数变化要单独解释，不能只提交成功截图。

完成标准：新环境按“`run_all.sql` 建 v0.1 → 备份/基线 → `run_migration.sql` 升 v1.0 → `regression.sql`”执行；存量环境按“备份现有 v0.1 → 基线 → 迁移 → 回归”执行。迁移入口不建空库、不删除存量库。两种路径都通过；合法写入成功、非法外码或数量被拒、越权失败均有断言；README、ER 图和数据字典对齐 v1.0。

README 的复现步骤在这一子阶段会从一步变两步，目录结构、脚本清单和文档索引都要跟着改。

### 5.1 迁移顺序、失败恢复与依赖对象

- C 编写 `sql/stage2/capture_baseline.sql`：在停止应用写入并完成备份后执行，保存迁移批次 ID、源码基线、对象定义摘要、业务键与关键行快照、金额/销量/库存结果、角色成员与对象权限。快照以持久化辅助表保存，不用跨连接会消失的临时表；一次成功捕获的批次不允许覆盖。A/B 提供本域采集 SQL，C 汇总；按订单键与明细键比较，不能只比总数。备份路径与恢复验证写入迁移说明，备份文件不入仓。
- C 维护辅助表 `dbo.SchemaVersion` 和 `dbo.MigrationBaseline`（详细列定义由 C 在迁移说明中冻结）。首次只在确认 v0.1 对象和完整基线后登记 v0.1；失败不留下伪造的 v1.0 标记。入口获取数据库级迁移应用锁并检查应用已停止写入；不满足前提即停止。
- `run_migration.sql` 使用 SQLCMD 遇错退出与 `SET XACT_ABORT ON`，在同一连接开启一个覆盖全部域脚本的事务。固定顺序为预检 → `11a` → `11b` → `11c` → C 的 `12_permissions.sql` → 事务内结构与数据不变量检查 → 版本标记 v1.0 → COMMIT。`GO` 允许分批，不得切换连接。域脚本不得 COMMIT 外层事务，失败回滚外层并 THROW；事务内检查只读，不运行会回滚外层的反例测试。
- A/B/C 的 `11*` 不仅迁移本域表，也升级本域存储过程、函数和视图；跨域外键由持有该外键的表属主升级。B 在重构方案列出被改字段的全部调用者；若 `11a → 11b → 11c` 无法满足依赖，必须在设计冻结时明确调整入口顺序，或增加按域命名的收尾脚本，在调用者全部升级后移除兼容结构。C 将确定的顺序和新增文件登记到 §7.1，不在运行时猜顺序；不能要求 `11a` 提前删除 C 尚在使用的对象。
- C 的 `12_permissions.sql` 在对象升级后重建必要授权，并为被 ALTER 的角色同步过程重新签名、验证签名有效。新增查询/上下文权限必须同时更新 `RolePermission` 权限代码 CHECK 白名单及映射种子，确认业务权限映射与实际 GRANT 一致。避免 DROP/CREATE 导致对象权限丢失；若确需重建对象，必须恢复原权限并核对差异。服务器登录名配置和数据库备份不属于该事务，使用独立的显式部署步骤。
- 重复运行策略：v0.1 正常升级；已为 v1.0 且迁移标识/结构摘要匹配时只报告已应用，不重复搬数据；未知版本、版本标记与实物不符、基线缺失或出现重复/断链数据时拒绝执行，输出具体业务键，不静默合并或删除。并发迁移只能一份成功取得应用锁。
- 失败恢复：提交前 SQL 出错或连接断开，整个迁移事务回滚，重新连接验证 v0.1 标记与基线后才能重试；提交后回归失败则停用应用，保留失败日志，在新的恢复数据库中还原已验证备份并核对基线，由操作者明确切换连接。不得自动覆盖原库或以删库重建恢复。C 提供一次域迁移中途故障与一次提交后恢复演练证据。
- 各域在 `13a/13b/13c` 提供提交后的可重复回归，C 的 `regression.sql` 顺序调用、汇总实际断言数并校验预期分母，非零退出即失败。沿用原错误编号，并同时记录原始文案；日志识别 `Msg`、`消息`、`Sqlcmd: Error` 和 `FAIL`。兼容性不变的第一阶段断言继续执行，受结构变化影响的断言在新增域回归中等价覆盖，不重写冻结的 v0.1 测试文件。

### 5.2 基线口径

A 的商品销量基线使用已取餐/已完成订单的 `SELLABLE` 项，按商品汇总数量和成交金额，套餐按销售父项计销量，子项单独列制作量而不重复计收入。B 保存订单、销售/组成明细、支付/退款、配送和积分快照，金额统一两位小数；C 保存现有/锁定/可售量、订单库存流水、采购收货进度、审计关联与权限映射。各域在重构方案中写清终态、时间区间、NULL 与套餐处理，再冻结采集 SQL；回归比较同一批数据，合法结构变化给出明确映射，不能改统计口径来消除差异。

## 6. 子阶段 2.3：应用开发

目标是把 v1.0 封装成按角色可操作的应用。教学安排把它拆成两块：访问层与核心业务接口、面向角色的界面与集成测试。

这一子阶段最大的风险是三个人各写一套连接方式和异常处理，所以先把访问层底座冻结，再各写各的模块。

| 成员 | 负责范围 |
| --- | --- |
| A | **访问层底座**：连接、参数化调用、统一错误与事务 helper；维护应用工程和依赖；主数据查询接口；管理员端商品、分类、原料、BOM、套餐、促销、会员等级、顾客维护；**操作手册** |
| B | 按收银/厨师/配餐/骑手拆分的订单界面、查询接口；店长取消退款界面；**事务边界规范**与**关键流程集成测试** |
| C | **员工登录、身份解析、权限守卫**与账号部署模板；员工角色维护；库存、补货、收货界面；岗位查询对象授权；**权限集成测试、测试入口和应用启动入口** |

底座交给 A 的理由：A 的主数据管理界面是最标准的 CRUD，用它验证 DAO 模板最直接，模板定型后 B 和 C 照着套即可。代价是 A 在这一子阶段的头几天成了关键路径，所以他只做一个最小骨架——连接、一个 DAO、异常、事务 helper——就冻结交付，不要一次做全。

作业的展示重点是"店员 / 管理员权限不同"和"关键流程可演示"，正好落在 C 的权限守卫与 B 的订单流程上，两人要提前把接口对齐。

交付物：连接配置、DAO/API、登录与基础 CRUD 界面、面向角色的操作界面、测试脚本、操作手册、可运行应用。

完成标准：用独立员工账号完成登录并由数据库返回真实身份；七个岗位按授权显示操作，绕过界面直接调用也被拒；能现场演示“新顾客建档 → 下单 → 支付 → 制作 → 自取/外送”，以及店长的取消/退款、补货审批和分批收货；应用业务值全部参数绑定；连接和错误处理统一走底座。登录失败、停用账号、跨骑手订单、故障回滚、注销换号与并发锁库都有测试证据。

### 6.1 登录与数据库身份契约（A/C 联合冻结）

本计划采用 .NET Windows 桌面应用、ADO.NET 与 SQL Server 存储过程。A 在骨架交付时固定目标框架、SQL 客户端包版本和 SDK，写进项目文件、`global.json` 与手册；不让三个模块各选一套框架。

默认演示采用**每个员工独立 SQL Server 登录名和同名映射数据库用户**，登录框接收账号/密码，直接用该身份连接数据库；这是现有 `USER_NAME()` 守卫可以直接工作的路径。C 在独立部署模板中创建登录映射和 `EmployeeAccount`，店长通过既有角色同步过程分配业务角色；登录密码只由操作者在本机提供，不写入脚本、配置、AI 记录或日志。服务端须已启用 SQL 身份验证，C 在应用开发前预检并写出配置步骤，应用和迁移不自动更改实例认证模式。若环境只能用 Windows 认证，则每个员工必须使用各自映射的 Windows 身份运行应用，并完成同样的岗位验收，不能让所有岗位共用当前 Windows 用户。

首次没有真实店长时，C 的部署模板由有权限的部署者创建一个真实店长账号/员工档案，并仅为该启动账号加入 `role_store_manager`；随后该店长通过角色同步过程补齐自己的业务映射、分配其他员工角色并产生审计。沿用 `09c` 的受控引导，不依赖应用登录不可用的测试店长，也不给普通员工开放角色管理权限。

`test_* WITHOUT LOGIN` 继续仅用于 SQL 断言，不作为应用可输入的登录账号；应用不得靠角色下拉框、员工 ID 参数或统一 dbo 连接冒充员工。多业务角色员工仍受过程中的 `job_code` 条件限制，角色分配界面必须提示这一点，不能承诺任意岗位叠加就能调用所有过程。

C 提供 `sp_get_current_employee_context`：无员工参数，按 `USER_NAME()` 返回唯一启用员工的 `employee_id`、数据库用户名、`job_code`、业务角色和权限代码（多角色/权限用独立结果集），无映射或已停用即拒绝。只授予七个业务角色 EXECUTE。A 连接成功后调用它，C 用其结果决定菜单和每次业务调用的权限守卫；业务过程继续独立校验身份，不信任界面传入的员工资料。

A 的连接工厂按登录会话持有身份，默认禁用连接池，每次操作打开短连接并在 finally/dispose 中关闭；禁止应用执行 `EXECUTE AS` 切换用户。注销或换号清空凭据、上下文、未提交购物车和窗口，重新认证；密码仅保留于当前进程必要生命周期。停用/撤权后下一次操作重新读取上下文并由数据库权限兜底。若后续启用池化，必须先通过“不同账号交替调用、异常退出后身份正确”的专项验收。

### 6.3 访问层与事务交接

A 在共享契约定义 `OpenConnection(session)`、`QueryProcedure(session, name, typedParameters)`、`ExecuteProcedure(session, name, typedParameters)`、`RunInTransaction(session, callback)` 的实际语言签名；参数显式指定 SQL 类型、长度、精度和 NULL，禁止字符串拼接值。统一错误包含 SQL 编号、原始消息与用户可读消息，保留原异常链，日志不含密码或完整连接字符串。

B 冻结事务规范：一次业务按钮通常只调用一个已自持事务的过程，不把下单、支付、制作、送达跨用户操作包进长事务；多过程原子操作才使用同一身份、同一连接的 helper。出现不可提交事务时外层完整回滚，不继续使用失败事务；异常时必须关闭连接。支付后网络中断视为结果未知，先查询订单/支付状态再决定是否重试，不自动重复写入。库存不足、重复支付、重复交付和两骑手竞争要有界面提示与集成测试。

A/C 首个联合验收交付：一个真实员工登录 → 上下文正确 → 一个允许的查询/写过程成功 → 一个未授权调用被数据库拒绝 → 注销后另一岗位身份正确；通过后 B/C 才按模板扩展界面。

## 7. 贯穿全程的约定

- 数据字典随改随更，谁的域谁更新；迁移和应用的字段变更都不许只改代码
- 回归脚本按域写、由 C 汇总，沿用第一阶段的验收口径：错误码加原始文案双核对，断言可重复执行，夹具不留在库里
- 每个子阶段结束时三人对一遍产出，上游定稿后才开下游
- **同仓分目录协作。** 各人只改自己域内的文件；合并类产物（总 ER 图、`run_migration.sql`、`regression.sql`）由主笔独占，另两人只提交自己那份素材，不直接改合并后的文件。`app/` 按域分目录，动别人的文件前先说一声
- **提交粒度按用途。** 一个提交只做一件事，不要把三个域的改动或"分析 + 迁移 + 界面"混在一起；动手前先拉一次最新，避免基于过期代码合图或合脚本
- AI 辅助过程各记各的，并入 `AI使用记录.md`

本节是成员 C 对 2026-10-10 版计划的评审补充：全部条目均为增补与建议，不修改本节以外的既有内容；讨论期以独立小节保留，2.1 收口时并入正文对应章节。

**13.1 §6.1 登录方案：实例事实与实验结论（关键路径）。** 实验与验证（2026-10-10，隔离库 `C_TEST_CONTAINED`，收尾后已清理）：① 包含用户机制可用且全部在线完成——`ALTER DATABASE ... WITH PASSWORD`（`authentication_type_desc = DATABASE`）、sysadmin 会话对其实施 `EXECUTE AS`、库属主不变。② **登录门在实例认证模式**：`IsIntegratedSecurityOnly = 1` 时错误日志实测“服务器配置为仅使用集成身份验证”，包含用户与普通 SQL 登录一样被拒——两条路径都躲不开“改实例认证模式 + 重启服务”（提权，约 2 分钟）；**包含用户不是“免重启”方案**（本文早期版本表述据此订正）。③ **本机已完成该项变更并验证**：混合模式（`LoginMode = 2`）重启后，包含用户 `ctest` 口令直连成功——`USER_NAME()` / `SUSER_SNAME()` / `ORIGINAL_LOGIN()` 均为 `ctest`、经所有权链执行存储过程正常、直读基表被拒“消息 229”；普通 SQL 登录同样可用。**本机实例保持混合模式供 2.3 使用**（还原 = `LoginMode = 1` + 重启）。④ C 的立场：默认演示路径采用**包含数据库用户**（免服务器级登录对象、随库复现），请 A 确认后与连接工厂一并冻结；`provision_employee.template.ps1` 按此写各成员机器的开启步骤与回退，部署预检只核对“实例为混合模式”。

**13.2 迁移事务中的签名还原——已实测并冻结结论。** 实验（2026-10-10，隔离库，DB 级 DMK + 证书 + 过程签名，形态同 `08`）：① `ALTER PROCEDURE` **立即丢弃**该对象已有签名（事务内即时可见，`sys.crypt_properties` 计数 1→0）；② **`ROLLBACK` 完整还原**——对象定义回到迁移前，被 `ALTER` 丢掉的签名随之恢复（计数回 1）；“ALTER + 重签 + 回滚”后状态与迁移前一致，**未出现“结构已回滚、签名残留”的混合态**；③ `COMMIT` 路径签名正常。**结论：签名步骤按普通事务成员对待——失败回滚到 v0.1 后不需要显式重建签名**，迁移说明的失败恢复一节引用本条。**边界**：判据为“定义文本 + `sys.crypt_properties` 计数”，未做低权限执行侧的签名生效性复验；如需更严，2.2 可补一次低权限执行探针。
