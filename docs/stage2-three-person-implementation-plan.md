# 第二阶段三人协作实施计划

**Goal:** 回头审查第一阶段的 v0.1 关系设计是否合理。用 ER 模型说明实体、属性、联系、基数和参与约束，用函数依赖与规范化论证现有结构的取舍，用迁移脚本修正确有问题的部分，再把数据库封装成按角色可操作的应用。

**Architecture:** 沿用第一阶段的三条业务线——A 主数据与定价、B 订单与履约、C 库存权限与集成。第二阶段不改这条线，改的是"从库到应用"的层次：库结构先经一次受控迁移升到 v1.0，再由统一的访问层封装，最后按岗位暴露操作界面。

**Spec:** 教学安排《第二阶段 · 第 5—9 周 数据设计、重构与应用开发》，含第五周（ER 模型）与第六周（函数依赖与规范化）两份讲解。库内依据为[业务流程](业务流程.md)、[数据边界清单](数据边界清单.md)、[角色与职能清单](角色与职能清单.md)与三份数据字典。

## 0. 阶段目标与三个子阶段

第二阶段按内容分成三个子阶段。作业的周次安排与它们一一对应，但本计划的推进、验收和分工一律按子阶段走，不按周次切分——一个子阶段里的产物归一个人负责到底，避免每周换手。

| 子阶段 | 目标 | 主要产出 |
| --- | --- | --- |
| 2.1 ER 模型重建 | 从 v0.1 反推 ER 模型，核对实体、联系、基数和参与约束，形成 v0.1 问题清单 | ER 图（可编辑源 + 导出图）、业务规则与映射清单、v0.1 问题清单、设计说明与验证记录 |
| 2.2 规范化与迁移 | 识别更新异常与函数依赖，判断范式，完成反规范化取舍与迁移设计 | 依赖与范式分析、重构方案、`migration.sql`、`regression.sql` 与回归结果 |
| 2.3 应用开发 | 实现访问层与核心业务接口，做成按角色可操作的应用 | 连接配置、DAO/API、登录与 CRUD 界面、角色界面、集成测试与操作手册 |

子阶段之间有依赖：2.2 的迁移依据是 2.1 的问题清单，2.3 的界面依据是 2.2 定稿的库结构。上游没定稿就动下游，返工量会大于等待成本。

## 1. 第二阶段新增的全局约束

第一阶段的全局约束继续有效，另有几条从本阶段开始生效：

- **第 6 周起不再删库重建。** 教学安排写明：删库重建会丢失已有数据，不能代替迁移；迁移前必须先备份或复制数据库。第一阶段的 `00_create_database.sql` 检测到同名库会主动 `THROW` 停下，这条保护现在正好用得上，不要为了跑迁移去删库。
- **迁移脚本不得删除已有业务数据。** 拆表、合表、改字段都要能带着基线数据走完，并且保留迁移前的结果快照供逐项比对。
- **README、数据字典、ER 图三处随改随更。** 迁移改了结构而文档没跟，第二阶段末会比第一阶段更难对账。
- **应用层一律使用参数化查询**，不得出现字符串拼接的 SQL。
- **连接凭据不入仓。** 应用需要连库时用集成认证或环境变量，沿用第一阶段"库中不留明文口令"的口径。
- 第一阶段关于 `unit_price` / `promotion_id` 必须是成交快照的约定不变，第二阶段的应用层不得绕过它反算历史订单。

## 2. v0.1 问题清单

第 5 周的正式交付物之一。这里先落两条已核实的问题，其余在第 5 周的实体与联系核对中补充。

### 2.1 已核实的保留项

**供应商实体不引入。** 教学安排把供应商列为待识别对象之一，但全库检索 `supplier` / `vendor` / 供应商 命中 0 处，`PurchaseOrder` 的 6 列（`purchase_order_id`、`purchase_order_no`、`replenishment_suggestion_id`、`purchase_status`、`approved_by_employee_id`、`approved_at`）里也没有 `supplier_id`，采购单发给了谁在库里无从回答。核对第一阶段业务流程后确认：从后台准备到补货闭环这条线上没有出现供应商选择、比价或到货评价，采购一律视为向门店唯一供应渠道补货。按"最简单的实现"的口径，第二阶段不扩展这个实体，理由记在此处备查。若日后要按供应商维度统计进价与到货质量，需要新增 `Supplier` 实体并给 `PurchaseOrder` 加外码，那是功能扩展，不是对现有设计的修正。

**成交价与促销命中是刻意的反规范化，保留。** `SalesOrderItem.unit_price`、`promotion_id` 存的是下单那一刻算出的值。商品编号能决定商品当前基价，但决定不了历史成交价；把快照拆掉改成关联 `Product.base_price` 现算，改一次价就会改掉所有历史订单的金额。教学安排正是拿这种情况举例，第 6 周分析函数依赖时按"保留并说明理由"处理。

**可售量不落列，保留。** `Inventory` 只有 `on_hand_qty`、`locked_qty`、`updated_at` 三列，可售量由前两者相减得出，没有单独的可售量字段。派生值不物化，就不会出现"账面量改了、可售量忘了改"的不一致。

### 2.2 待处理项

**"每张订单至少有一条明细"缺少约束保证。** 教学安排专门提醒过：外码保证引用对象存在，但不自动保证每张订单至少有一条明细，要求区分数据库现有约束与业务要求。当前 `SalesOrder` 上只有 4 条 `CHECK`（`order_status`、`fulfillment_method`、`total_amount`、`pickup_code`），没有任何一条约束明细条数。`sp_create_order` 在下单路径上必然会写明细，但那是过程的自觉，不是数据库的约束——绕过过程直写就得不到保证。第 6 周要决定是补触发器或改用其他手段，还是明确接受为已知限制并写进报告。

**`SalesOrder.total_amount` 与明细金额之和重复，需要给出口径。** 抽查存量三张订单，`total_amount` 与 `SUM(unit_price × quantity)` 逐张相等，说明当前是冗余存储而非独立口径；同时没有任何约束或触发器保证两者一致，直写明细就会脱节。第 6 周要二选一：要么给出必须存总价的理由（例如总额含订单级优惠、需要冻结），要么改为由明细求和并删除该列。这条不预设结论。

### 2.3 第 5 周补充

问题清单不止上面四条。第 5 周做实体与联系核对时，重点盯这几类：实体遗漏（某个业务对象没有对应表）、属性重复（同一事实存在两处）、联系表达不清（该用关联表的用了可空外码，或反之）、以及基数写错（因样例数据恰好一对一就认定业务上是一对一）。

## 3. 分工原则

**域主不变。** 第一阶段的分工按业务线划，第二阶段继续沿这条线：A 主数据、定价与会员，B 订单、支付与履约，C 库存、补货、权限与集成。理由很实际——ER 的实体、函数依赖的候选码、数据字典的属主都是按域走的，换人等于把别人的表重新读一遍，而第二阶段的三个子阶段都要用到这个域内知识。

**跨域产物归 C。** 延续第一阶段 `run_all.sql` 与测试报告的角色：三个域之间的联系人、合并后的总图、迁移入口脚本、回归脚本汇总、权限侧集成测试，都由 C 主笔，但断言的内容由各域主人提供。

**一个产物只有一个主人。** 合并类工作（总 ER 图、`regression.sql`）由 C 主笔，其余两人只提交自己域内的素材，不直接改合并后的文件，避免同一份文件两头改。

## 4. 子阶段 2.1：ER 模型重建

目标是把 v0.1 的 25 张表还原成规范的 ER 模型，并解释每一处设计的合理性或问题。

| 成员 | 负责范围 |
| --- | --- |
| A | 主数据域 10 张表的实体、属性、主标识与候选标识清单；该域问题清单；**并负责 ER 图命名与三份数据字典的对齐** |
| B | 订单域 5 张表同上；**基数与参与约束总口径**；问题清单 2.2 第 1 条由 B 落笔 |
| C | 库存权限域 10 张表同上；**跨域联系统一口径**；**合并总 ER 图与符号图例**；问题清单 2.1 第 1 条由 C 落笔 |

A 之所以兼管命名对齐：教学安排要求"图中命名能对应到数据字典"，而三份数据字典分属三人，需要一个总口径来统一实体名、属性名与联系名的写法。

这一子阶段**只动 `docs/`，一行 `sql/` 都不改**。教学安排写得很明确：本周先完成分析与问题清单，保留可复现的 v0.1，结构调整留到第 6 周由迁移脚本实施。

交付物：

- `docs/er/` 下的 ER 图源文件（可编辑）与导出图，附符号图例
- 业务规则与映射清单：逐条写明联系两端的最小 / 最大基数、适用条件、对应表与外码，以及该规则当前由约束、代码还是人工检查实现
- v0.1 问题清单（即本文第 2 节）
- 设计说明与验证记录：展示多商品订单、会员或散客购买、库存查询三类情形在图和库中的对应关系

完成标准：三人各自的子图与问题清单齐备；总图合并后 25 张表与 35 条外键全部在图上有落点；图中命名能逐一对应到数据字典；每条保留项都写明了理由，每条待改项都指向第 6 周。

## 5. 子阶段 2.2：规范化与迁移

目标是在 v0.1 的副本上跑通一次受控迁移，证明迁移前后业务含义一致。

| 成员 | 负责范围 |
| --- | --- |
| A | 主数据域逐表：候选码 → 关键函数依赖 → 1NF/2NF/3NF 判断 → 分解或保留理由；`11a_master_migration.sql`；更新主数据数据字典；**商品销售统计的迁移前基线** |
| B | 订单域同上；`11b_order_migration.sql`；更新订单履约数据字典；**订单明细的迁移前基线** |
| C | 库存权限域同上；`11c_inventory_security_migration.sql`；更新库存权限数据字典；**库存查询的迁移前基线**；**`run_migration.sql` 入口与 `regression.sql` 汇总** |

迁移脚本按域拆成三份再串一个入口，与第一阶段 `10a` / `10b` / `10c` 的写法保持一致。脚本内容按教学要求覆盖：新表创建、字段调整、主码候选码外码设置、必要的数据迁移、重复数据检查、旧表处理或保留说明。

范式判断的几条口径要提前统一，免得三人各判各的：检查 2NF 要看所有候选码，不能只看主键；判断 3NF 要分析非平凡函数依赖的决定因素，不能只盯着主码；样例里没有重复值不等于依赖不成立；表不是越多越好，现有结构合理就保留并给出分析证据，需要演示异常时另建独立的关系示例，不要为了展示规范化而破坏原项目。

迁移前必须先备份或复制数据库。回归脚本要覆盖关键标识、关系映射、订单金额、商品销量、库存和角色权限，逐项记录迁移前基准、预期值、迁移后结果与差异解释。拆表带来的行数变化要单独解释，不能只提交成功截图。

完成标准：`run_all.sql` 建出 v0.1、`run_migration.sql` 升到 v1.0，两条路径都能从空库跑通；`regression.sql` 全项通过；合法写入成功、非法外码或数量被拒、越权操作失败三类断言都有；README、ER 图与三份数据字典同步到 v1.0。

README 的复现步骤在这一子阶段会从一步变两步，目录结构、脚本清单和文档索引都要跟着改。

## 6. 子阶段 2.3：应用开发

目标是把 v1.0 封装成按角色可操作的应用。教学安排把它拆成两块：访问层与核心业务接口、面向角色的界面与集成测试。

这一子阶段最大的风险是三个人各写一套连接方式和异常处理，所以先把访问层底座冻结，再各写各的模块。

| 成员 | 负责范围 |
| --- | --- |
| A | **访问层底座**：连接配置、DAO 模板、参数化查询封装、统一异常处理、事务 helper，先做完并冻结接口；管理员端界面（商品、分类、BOM、套餐、促销、会员等级维护）；**操作手册** |
| B | 店员端界面（点单、支付、制作、取餐与外送）；**事务边界规范**，对齐第一阶段各过程的事务语义；**关键流程集成测试** |
| C | **登录与身份权限守卫**（对应 `EmployeeAccount` / `BusinessRole` / `RolePermission`）；库存、补货、收货端界面；**权限侧集成测试与测试脚本汇总** |

底座交给 A 的理由：A 的主数据管理界面是最标准的 CRUD，用它验证 DAO 模板最直接，模板定型后 B 和 C 照着套即可。代价是 A 在这一子阶段的头几天成了关键路径，所以他只做一个最小骨架——连接、一个 DAO、异常、事务 helper——就冻结交付，不要一次做全。

作业的展示重点是"店员 / 管理员权限不同"和"关键流程可演示"，正好落在 C 的权限守卫与 B 的订单流程上，两人要提前把接口对齐。

交付物：连接配置、DAO/API、登录与基础 CRUD 界面、面向角色的操作界面、测试脚本、操作手册、可运行应用。

完成标准：应用能演示登录；店员与管理员看到的操作范围确实不同，越权入口被挡住；下单到取餐或外送的主流程可现场演示；全代码库无字符串拼接的 SQL；连接与异常处理统一走底座。

## 7. 贯穿全程的约定

- 数据字典随改随更，谁的域谁更新；迁移和应用的字段变更都不许只改代码
- 回归脚本按域写、由 C 汇总，沿用第一阶段的验收口径：错误码加原始文案双核对，断言可重复执行，夹具不留在库里
- 每个子阶段结束时三人对一遍产出，上游定稿后才开下游
- AI 辅助过程各记各的，并入 `AI使用记录.md`

## 8. 开工前置项

三件事没定，后面的活就不好分：

1. **ER 图工具**——第 5 周第一天定一个（Freedgo、Visio、drawio 均可），统一符号与文件格式，否则合图时对不上
2. **应用技术栈**——第 6 周结束前必须定，它直接决定 2.3 怎么拆。教学安排不限语言；本项目库是 SQL Server，选 .NET 最顺（集成认证直连、调用存储过程方便），Java 或 Python 也可行
3. **应用代码的落位与配置方式**——新增 `app/` 之后要补 `.gitignore`（编译产物、依赖目录、虚拟环境），并把连接凭据挡在版本库外

## 9. 已知风险

**第 6 周是三段里最紧的。** 它要在不能删库重建的前提下同时完成范式分析、迁移实施和回归验证。如果第 5 周的 ER 与问题清单做得含糊，第 6 周会连带塌。建议第 5 周收尾时三人当场定下"哪些改、哪些保留、理由是什么"，第 6 周只管实施。

**应用阶段的分层容易散。** 三人各写界面时最容易各带一套数据库访问代码。底座必须在 2.3 开头几天内冻结，并且冻结后只允许 A 一个人改。

**迁移与应用可能同时被改。** 如果库结构在 2.3 期间又发生变动，应用层的字段映射会集体失效。第 6 周之后库结构应视为冻结，再有调整需要三人同意并同步改回归脚本。
