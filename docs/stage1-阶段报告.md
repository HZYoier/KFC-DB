# 第一阶段阶段报告：KFC 门店运营数据库（v0.1）

本报告是第一阶段的总报告，覆盖经营场景、数据边界、表设计、完整性约束与角色权限，以及空库部署与验收过程。成员 A（24325106 胡志远）、B（24325328 张奕希）、C（24325108 黄柏源） 各自的实现细节见[成员 A 阶段报告](stage1-a-stage-report.md)、[成员 B 阶段报告](stage1-b-stage-report.md)、[成员 C 阶段报告](stage1-c-stage-report.md)，验收数字与复验记录见[第一阶段测试报告](stage1-test-report.md)。对应代码为 `sql/` 下的 18 个部署脚本，唯一入口是 `sql/run_all.sql`。

## 1. 设计思路

### 1.1 经营场景与业务流程

系统以一家 KFC 门店的经营链路为原型，从后台准备一直走到补货闭环，业务主线共 8 步，完整叙述见[业务流程](业务流程.md)。这里按"每一步往库里写什么"重新梳理一遍，因为表结构基本上是被这条链推出来的。

店长在后台录入商品名称、分类和标准基价，为每个商品绑定物料清单 BOM（一个香辣鸡腿堡需要一片面包、一块鸡腿肉、一片生菜），再配置促销规则，比如疯狂星期四是每周四 9.9 元一口价。这一步写进 `Product`、`Category`、`ProductCategory`、`ProductBom`、`Promotion` 和 `PromotionProductRule`。

顾客点餐时系统先识别身份（散客、WOW 会员、付费会员），再由价格引擎按当前时间匹配促销：命中就显示活动价并标注来源，没命中就显示基价；套餐按 `ComboComponent` 拆成子商品再累计总价。确认下单后生成订单主表和订单明细。明细里存的是下单那一刻算出的成交价和命中的促销 ID，不是等查询时再算。同一个事务里还要按 BOM 把这次订单要用的原料锁住，库存表的锁定量加上用量，账面量不动。

支付成功后订单从 `PENDING_PAYMENT` 变到 `PAID`，写 `Payment`，同时生成一条状态为 `PENDING` 的积分流水，此时不累加到会员总积分。制作完成时锁定量转成实扣，账面量和锁定量同时减去用量，`InventoryMovement` 记一笔，订单按 `fulfillment_method` 变成 `READY_FOR_PICKUP` 或 `READY_FOR_DELIVERY`。取餐或送达后订单进终态（`PICKED_UP` 或 `COMPLETED`），这时才把积分流水从 `PENDING` 改成 `EFFECTIVE` 并累加到 `Customer.current_points`，再按门槛判断要不要升级。库存每次扣减后都比对安全库存线，低于就自动生成补货建议单，值班经理提交、店长审批后生成采购单，分次收货回补库存。未支付取消或实扣前退款则释放锁定量，订单标记 `CANCELLED`，待生效积分作废。

这条链上有三个判断对表结构的影响最大。一是成交价必须落成快照而不是视图现算，否则日后改价或改活动规则会改到历史账。二是防超卖锁在下单那一刻而不是支付之后，所以库存表必须同时持有账面量和锁定量两个字段，可售量只能由两者相减得出。三是积分走两段式，支付时只生成待生效流水，进终态才落账，这样重复到账在结构上就不好发生。

### 1.2 哪些信息进入数据库、哪些不进入

判据只有一条：需要追溯、统计或审计的进，其余不进。完整清单见[数据边界清单](数据边界清单.md)，这里说明归类的理由。

进入数据库的是核心业务事实，分六个域：商品与配方（商品、分类、套餐组成、BOM、原料及安全库存线），促销与定价（促销活动加促销商品规则），顾客与会员（顾客主档、会员等级、积分倍率、等级门槛），订单与履约（订单主表与明细、支付记录、积分流水、配送记录），库存与补货（库存表、库存变动流水、补货建议单、采购单与收货记录），以及账号权限（员工账号、业务角色、角色权限映射、审计日志）。这些要么是价格引擎与下单的前提，要么是锁库存扣库存的依据，要么本身就需要留痕。

不进入数据库的可以归成四类。一是可派生或纯会话态的数据：购物车中间态在结算那一刻才生成订单，落库价值低；后厨 KVS 队列完全由订单状态实时派生，另存一份只会双写不一致。二是非结构化或文档范畴的数据：制作工艺的火候、油温、时长属于 SOP 文档，库只存"用什么料"不存"怎么做"。三是设备间实时消息和第三方数据：叫号广播、取餐屏推送是短消息，取餐码本身已经在订单表里；骑手 GPS 轨迹属于第三方运力平台，只留取餐和送达两个时间点就够追溯。四是安全合规要求不能留的：第三方支付的完整报文、卡号、密钥只取业务字段和流水号，凭证留在支付平台；会员密码只存哈希或交给认证服务。此外小票打印格式、界面布局、通知文案属于展示层，与业务数据无关。

有两处属于灰色地带。散客我们选择照常建档，否则订单没有 `customer_id`，后续按顾客维度分析无从谈起，另设了 `TEMP-` 开头的游客临时号过渡。每日销售和经营汇总本阶段不建表，OLTP 里不预留派生聚合，避免手工维护对不上，这部分留到后续阶段做分析视图。

### 1.3 表设计：主码

全库 25 张用户表都有主键，形态分三种。

18 张表用单列代理主键，类型 `BIGINT IDENTITY(1,1)`，例如 `Product.product_id`、`SalesOrder.order_id`。这里没有拿业务字段当主码，是因为业务标识会变：商品名会改、手机号会换、订单号在补录场景可能重编，而主码一旦被别的表引用就不能再变。代理键把可变和不可变分开，业务字段照常改，指向它的外键不受影响。

1 张表的主码同时就是外码：`Inventory` 的主码是 `ingredient_id`，它也是指向 `Ingredient` 的外键。库存是原料的补充属性，一种原料至多有一行库存，属于一对一扩展表，让主键本身充当那个外键，一对一的基数由主键唯一性直接保证，不需要再对同一列另建唯一约束。

剩下 6 张是纯关联表，用复合主键：`ProductCategory(product_id, category_id)`、`ProductBom(product_id, ingredient_id)`、`ComboComponent(combo_product_id, child_product_id)`、`PurchaseOrderItem(purchase_order_id, ingredient_id)`、`EmployeeBusinessRole(employee_id, business_role_id)`、`RolePermission(business_role_id, permission_code)`。这几张表的全部意义就是两边同时存在，自身没有属性需要被别的表引用，再补一个无意义的代理 ID 只会多一列索引，还要额外建唯一约束去防止重复关联；用复合主键则重复行在结构上插不进去。复合主键的组成列由主键隐式保证非空，脚本里不再重复声明。

### 1.4 表设计：候选码

候选码用 `UNIQUE` 约束表达，共 9 条，都是业务上的唯一标识：

| 表.列 | 约束名 | 业务含义 |
| --- | --- | --- |
| `Customer.mobile` | `UQ_Customer_Mobile` | 顾客按手机号唯一，游客用 `TEMP-` 号段同样唯一 |
| `SalesOrder.order_no` | `UQ_SalesOrder_order_no` | 订单业务号唯一 |
| `PurchaseOrder.purchase_order_no` | `UQ_PurchaseOrder_purchase_order_no` | 采购单业务号唯一 |
| `EmployeeAccount.login_name` | `UQ_EmployeeAccount_login_name` | 登录名唯一 |
| `EmployeeAccount.database_user_name` | `UQ_EmployeeAccount_database_user_name` | 数据库主体名唯一 |
| `BusinessRole.role_code` | `UQ_BusinessRole_role_code` | 角色代码唯一 |
| `Payment.order_id` | `UQ_Payment_order_id` | 一个订单至多一条支付记录 |
| `Delivery.order_id` | `UQ_Delivery_order_id` | 一个订单至多一条配送记录 |
| `PointLedger.order_id` | `UQ_PointLedger_order_id` | 一个订单至多一条积分流水 |

其中 `EmployeeAccount.database_user_name` 这条不只是唯一标识，它还是过程内身份解析的依据：每个写过程都按 `USER_NAME()` 反查这张表来确认调用者是谁，所以这一列必须唯一，否则身份解析会有歧义。

后三条落在 `Payment`、`Delivery`、`PointLedger` 上，把指向订单的外键同时约束成唯一，作用是把一对多收窄成一对一——支付重复写入、配送单重复生成、积分重复到账这三类错误因此在结构层就写不进去，不需要靠过程自觉。

另有 3 条过滤唯一索引，可以理解为带条件的候选码，表达的是"在某个子集内唯一"。`UQ_ProductCategory_is_primary` 带条件 `is_primary = 1`，保证每个商品至多一个展示分类，同时允许它挂任意多个次要分类；`SalesOrder.pickup_code` 的唯一索引带条件 `pickup_code IS NOT NULL`，让取餐码只在已分配的行内唯一，未分配的行不参与；`ReplenishmentSuggestion.ingredient_id` 的唯一索引带条件 `suggestion_status IN ('PENDING','SUBMITTED','APPROVED')`，保证每种原料至多一张开放中的建议单，历史已关闭的不受限制。这三条普通 `UNIQUE` 做不到，因为普通唯一约束会把次要分类行、未分配取餐码行、历史建议单一起算进去，把合法数据也拦下来。

这些候选码都没有被选作主码，原因有两个：它们全都可变，且其中多条本身就被外键引用。取"代理主键作主码、业务唯一列作候选码"的组合，既保住引用的稳定性，又让业务唯一性由数据库强制。

### 1.5 表设计：外码

全库 35 条外键，覆盖所有跨表引用，包括跨域的几条：`Inventory → Ingredient`、`SalesOrderItem → Product` / `Promotion`、`Delivery → EmployeeAccount`。

这 35 条全部是 `NO_ACTION`，没有一处级联删除。这是有意的：订单、支付、积分、库存流水都是历史账，主数据也一律只停用不删除（`status` 置 `INACTIVE`），正常业务里父行根本不会被删，级联规则没有用武之地；而 `NO_ACTION` 会把误删父行变成一条显式报错，比 `CASCADE` 静默连带删掉一批历史记录安全。删除父行的唯一可能是误操作，这种情况下应该失败而不是静默扩散。

其中 `FK_SalesOrderItem_Parent` 是自引用外键，`SalesOrderItem.parent_order_item_id` 指回 `SalesOrderItem.order_item_id`，用来表达套餐和它子项的层级：套餐父项一行，子项若干行挂在它下面，单品这一列为 `NULL`。父子由 `item_role` 区分（`SELLABLE` 或 `COMPONENT`），`CK_SalesOrderItem_item_role` 还规定 `COMPONENT` 行必须 `unit_price = 0` 且 `promotion_id IS NULL`，也就是套餐子项不单独计价、价格只记在父项上，从结构上排除了子项重复计入金额的错误。另外 `FK_Delivery_RiderEmployee` 是可空外键，因为自取订单没有骑手。

### 1.6 完整性约束：角色与权限如何划分

权限分两层。

第一层在数据库层，7 个业务角色配 7 个不带登录的测试用户，共 52 条精确到过程或视图的 `GRANT`，以及 21 行 `DENY`。各角色的授权数是：店长 `role_store_manager` 35 条，值班经理 `role_shift_manager` 8 条，收银员 `role_cashier`、厨师 `role_chef`、配餐员 `role_packer`、骑手 `role_rider` 各 2 条，服务员 `role_waiter` 1 条。所有业务写入都只走存储过程，不向任何业务角色开放表级写权限，所以 `GRANT` 全部落在过程和视图上。

21 行 `DENY` 是 3 条规则乘 7 个角色，用来堵绕过过程直接改敏感字段这条路。`Inventory` 上是表级 `DENY UPDATE`，任何角色都不能直接改库存两列，必须走库存过程；`Customer.current_points` 和 `SalesOrderItem.unit_price` 上是列级 `DENY UPDATE`，分别禁止直接改顾客积分和篡改成交价快照。

第二层在过程内部。每个写过程都按 `EmployeeAccount.database_user_name = USER_NAME()` 反查当前员工，确认它是启用的并且具备相应业务角色，解析不到就 `THROW 51004` 拒绝执行，不信任外部传进来的主体参数。两层是纵深关系：数据库层管"能不能调用这个对象"，过程层管"调用者到底是谁、有没有资格"。只靠第一层挡不住"有调用权但身份不对"，只靠第二层则任何能连上库的人都能绕过。另外，角色分配过程需要 `ALTER ANY ROLE` 这类高权限，这部分交由证书签名主体代持，没有直接授予业务角色。

正例方面：店长可以调用全部 18 个主数据 CRUD 过程，也可以审批补货建议生成采购单；收银员可以创建订单、写支付记录、发起退单；厨师可以把订单迁到制作中；配餐员可以完成制作并出餐；骑手可以确认分配给自己的配送单；顾客积分由 `sp_apply_customer_points` 在订单终态写入。反例都是可重复执行的回滚型断言，覆盖的情况包括：店长直接 `SELECT` 主数据表返回 `消息 229`（有过程执行权但没有表读权）；收银员直接更新 `SalesOrderItem.unit_price` 返回 `229`（列级 `DENY` 生效）；任何角色直接更新 `Inventory` 返回 `229`（表级 `DENY` 生效）；有对象权限但没映射到启用员工的主体调用写过程抛 `51004`；骑手确认他人配送单返回 `52702`；值班经理调用角色分配过程被拒（`10c` 的 T14 断言）。

### 1.7 完整性约束的分层

约束分三层落地，越靠前的越先拦。列级是 51 条命名 `CHECK`，负责行内谓词：数值正负、取值枚举、时间先后、格式。表级是 9 条唯一约束、3 条过滤唯一索引和 35 条外键，负责唯一性、基数和引用完整性。过程级是 42 个存储过程里的业务规则，负责跨行跨表的判断，比如上架前必须有 BOM、套餐不能配直接 BOM、积分不能为负，违反时抛 `51xxx` 或 `52xxx`。

有一点配合关系容易忽略：`CHECK` 的表达式在 `NULL` 上求值为 `UNKNOWN`，会被直接放行，所以受约束的列一律显式声明非空，光有 `CHECK` 拦不住空值。A 域 10 张表里唯一的可空列是 `Customer.member_level_id`，它的含义是等级被停用后置空。

另有一条原则是入口拦截优先于事后校验：单品没有用料、套餐有子项缺 BOM，一律不许置为 `ACTIVE`，而不是等到下单时才发现做不出来。

需要说明的是，因为过程会先做业务校验并抛出 `51xxx`，原生约束在正常路径上很少被触发，比如负数价格会先被过程拦下，`CK_Product_base_price` 不会报错。所以验收时专门补了一条绕过存储过程、直接 `INSERT` 的用例，用来证明过程自查之外的原生约束确实在拦：`547` 命中 `CK_Product_base_price`、`CK_Product_status`、`CK_Product_product_type`，`2627` 命中 `UQ_Customer_Mobile`。

## 2. 实验过程

### 2.1 环境

数据库平台为 SQL Server 2025（17.0.1000.7），兼容级别要求不低于 130，实际部署后 `KFC_DB` 的兼容级别为 170，全部对象使用 `dbo` 架构。登录使用 Windows 身份验证，部署账号需要建库权限。客户端用 `sqlcmd`（ODBC Driver 18）。

执行命令必须带 `-C -f 65001 -b` 三个参数。`-C` 是因为 ODBC Driver 18 默认强制加密，而本地实例用的是自签证书，不加会报证书链不受信任；`-f 65001` 是因为 `sql/` 下的脚本是 UTF-8 无 BOM，不加会按代码页 936 解码，中文字符串字面量被静默读错，种子会写成乱码而且不报错；`-b` 让任一 SQL 错误返回非零退出码，这是"空库部署成功"可以判定的前提。

### 2.2 空库部署

删除目标实例中的 `KFC_DB` 后，在仓库根目录只执行唯一入口：

```powershell
sqlcmd -S localhost -E -N o -C -f 65001 -b -i "sql/run_all.sql"
```

`run_all.sql` 按固定顺序串联 18 个文件：`00 → 01 → 02 → 03 → 04 → 06 → 05 → 07a → 07b → 07c → 08 → 09a → 09c → 09b → 09d → 10a → 10b → 10c`。顺序不能随意调换，`04`（A 的过程）会调用 `06`（C 的审计过程）里的 `sp_write_audit_log`，所以 `06` 必须排在 `04` 前面；三个建表脚本都带指向 A 的表的外键，所以 `01` 必须最前。`04` 在 `06` 之前会打印 11 条"取决于缺少的对象"，这是冻结顺序下的已知编译告警，不是错误——SQL Server 建过程时不检查被调对象是否存在。

整跑一遍即得到空库部署的现场：先是 `KFC_DB 创建完成，兼容级别 = 170`，随后依次建表、建过程、建视图、授角色权限、灌种子、跑三域验收，全程无 SQL 错误。这一过程的操作截图见 [`result/stage1-a-create-database-2026-10-04.png`](../result/stage1-a-create-database-2026-10-04.png)，对应的完整日志是 [`result/stage1-full-test-a-2026-10-04.txt`](../result/stage1-full-test-a-2026-10-04.txt)。

`00_create_database.sql` 检测到同名库会主动 `THROW 50000` 停下，不覆盖已有数据，所以"重建"必须由人先删库；这一步是刻意的，避免把已经验收过的数据无声冲掉。

### 2.3 验收结果

三个域的验收脚本都从零失败通过：`10a`（主数据、定价与会员）`pass=13 fail=0`，`10b`（订单、支付与履约）`pass=15 fail=0`，`10c`（库存、补货、权限与集成）`pass=18 fail=0`，合计 46 条，加上日志里的 `PASS: B seed orders` 共 47 条 `PASS:`，SQL 错误 0 条，`sqlcmd` 退出码 0。

断言统一按"错误码加原始文案双核对"写，各自成批、事务包裹一律回滚，夹具不留库里，跨批次用临时表计数并在收尾设分母守卫，专门抓"某一批被静默作废"这种不报错的失败。E2E-01 到 E2E-07 七个场景（周四促销下单、制作取餐、外送送达、未支付取消、原料不足回滚、低库存补货、权限越权）全部有结论。

### 2.4 跨域接口契约

三个域之间只经冻结的接口交互，不互相直写。A 向 B 提供 `fn_get_effective_product_price`（读，定价）和 `sp_apply_customer_points`（写，积分）；C 向 B 提供 `sp_lock_order_inventory`、`sp_release_order_inventory`、`sp_consume_order_inventory`（锁库、释放、实扣）和 `sp_receive_inventory`（收货，第三个参数可选）。

定价判断只有一处实现，促销的启用状态、日期范围、星期、时段四重匹配全部收在内联表值函数里，视图和 B 的 `sp_create_order` 都调它，不复制规则。星期映射用 `DATEDIFF` 而不是 `DATEPART(WEEKDAY, ...)`，后者受 `SET DATEFIRST` 影响，换台机器结果就变。只读检查器 `sql/contract_interface_check.sql` 逐字校验对象名与类型、参数名类型序号个数、返回列和元数据精度（含 `@at` 的 `datetime2(0)`、`max_length = 6`），独立执行返回 `PASS`。

### 2.5 权限与失败路径的正反验证

权限用 `EXECUTE AS USER` 做正反探针：越权读表返回 `229`，越权直接更新敏感列返回 `229`，骑手确认他人配送单返回 `52702`，未映射主体调用写过程抛 `51004`，合法岗位的调用全部成功。

失败路径的收尾顺序在本阶段固化成了可重复执行的写法：先 `ROLLBACK`，再 `REVERT`，最后重抛原错。原因是 `run_all.sql` 是单会话执行，`02` 里的批次级 `SET XACT_ABORT ON` 会一直留到验收脚本，此时过程内的 `THROW` 会把外层事务打成不可提交（`XACT_STATE() = -1`），而在不可提交事务里 `REVERT` 会被拒（`Msg 3930`）并中止整批，把原始错误盖掉。

### 2.6 独立复验

合并后的 `main` 在三台不同机器上分别从空库整跑，结论一致，分别是成员 B 的 `localhost\MSSQLSERVER2`、成员 C 的 `.\SQLEXPRESS` 和成员 A 的 `localhost`。三台的实例类型和版本不完全相同（Developer 和 Express 都有），相同的是"删库、单入口执行、`exit=0`、三条验收结果、契约检查通过"这条链。成员 C 另外做了四条域内夹具链的 144 条断言回归（0 FAIL）、`08` 连跑两遍幂等、`09c` 重跑被守卫 `THROW 51001` 拒绝（预期）。

## 3. 实验总结

### 3.1 结论

第一阶段的目标已经达成。`KFC_DB` 能从空数据库一次部署表、约束、存储过程、查询视图、种子数据和岗位权限，并在三台独立机器上得到一致的验收结果：A `13/13`、B `15/15`、C `18/18`，共 47 条 `PASS`、0 条 SQL 错误，跨域接口契约检查通过。

具体来说，主数据域能独立表达品类、商品、套餐、原料与 BOM、促销和会员关系，也能让订单域凭冻结的种子 ID 直接下单、让库存域凭 BOM 算出订单用料；订单域的履约状态机、库存域的锁定释放实扣与补货闭环、权限域的最小权限与审计，都在同一套库里可运行、可回滚、可追溯。

### 3.2 主要设计取向

动手之前先划边界，再建表。购物车、KVS 队列、GPS 轨迹这类派生或外部数据不进库，避免双写不一致；成交价快照、命中促销 ID、库存变动流水这类要追溯的数据必须落库，不能靠视图现算。

不变的东西用代理键，可变的东西用候选码。主码取 `BIGINT IDENTITY` 保证引用稳定，业务唯一性交给 `UNIQUE` 约束；对"子集内唯一"的需求（主分类、取餐码、开放建议单）用过滤唯一索引，避免普通唯一约束误伤合法数据。

约束分层，各管一段。行内谓词交给 `CHECK`，唯一性和引用完整性交给表级约束，跨行跨表规则交给过程，三者不互相顶替。

入口拦截优先于事后校验，配置不完整的商品根本不允许上架，而不是等到下单才暴露。权限上采用最小权限加纵深防御，业务写入只经存储过程不开放表级写权限，数据库层管能不能调用，过程内再管是谁在调用。验收环节把"没有假绿"放在第一位，错误码和原始文案双核对，断言各自成批、事务一律回滚、跨批次设分母守卫。

### 3.3 已知限制

有一处权限机制的边界需要记录：`DENY` 只约束直接 DML，穿过所有权链不生效。业务角色被 `DENY UPDATE Inventory` 之后，仍然可以通过 `dbo` 拥有的存储过程间接改动库存。这正是"所有写入必须经过程"这条设计成立的原因，也说明权限真正的执行点是过程内部的身份校验，而不是 `DENY` 本身。

过程反例报的是 `51xxx` 而不是原生约束的错误码，因为过程会先做业务校验，正常路径上 `CHECK` 和 `UNIQUE` 很少被触发，这一点在 §1.7 里已用一条绕过过程直写的反例补上证据。

本阶段不建统计和分析视图，10 个视图都是明细或看板视角，只有 `v_product_bom_detail` 带聚合。每日销售与经营汇总按边界清单的取向属于派生聚合，留到后续阶段做成分析视图，避免在 OLTP 里手工维护对不上。

主码、候选码、外码的设计理由此前分散在三份数据字典里，术语也混用了"主键/外键"，§1.3 到 §1.5 按主码、候选码、外码的口径重新集中论述了一遍。另有制作工艺、骑手 GPS、第三方支付报文刻意不入库，理由见 §1.2。

### 3.4 后续阶段

主数据与订单、库存的关系模型已经稳定，下一阶段在这个基础上补补货预测和经营分析：目前刻意留在库外的每日销售汇总，届时以分析表或物化视图的形式补上；`InventoryMovement` 的流水已经按单据号留全，可以直接用于预测。
