## （2026-09-09）——KFC 角色枚举、精简评估与补全

**聊了什么：** 我让 AI 列出 KFC 门店中所有角色与职能（如店长、店员、会员）。AI 按"门店运营层 / 管理层 / 后台支持层 / 外部角色"四层枚举了 21 个角色（服务员——细分外场/内场/咖啡师、训练员、收银员、配餐员/总配员、厨师、厨师长、楼面经理、值班经理、副经理、资深副经理、储备经理、餐厅经理/店长、区经理、人力/财务/采购专员、散客、WOW 会员、付费会员、品牌挚友、第三方骑手）。我又追问：若只做单店的基本经营闭环，选训练员、收银员、配餐员、厨师、值班经理、餐厅经理、HR、散客、WOW 会员、付费会员这 10 个角色是否足够。

**AI 做了什么：** 逐项代入业务流程"沙盘推演"，确认这组角色能跑通 下单→制作→配餐→收银→值班管理→会员留存 的核心闭环，但指出两个缺口——缺基础"服务员"（外场基础勤务若让训练员/收银员兼任，权限设计上冗余）；缺"第三方骑手"（若做外送，订单履约的已取餐/配送中状态会缺关联数据）。

**我的处理：** 采纳建议，**新增"服务员"与"第三方骑手"两个角色**，角色体系补全，并按照选择的角色职责进行整理，再让AI进行补充和扩展。

## （2026-09-09）——业务全貌梳理 + 两份设计清单

**聊了什么：** 把项目背景讲给 AI：以现实 KFC 门店为原型，维护一个数据库，平台 SQL Server。业务主线是后台准备 → 顾客点餐计价 → 下单支付 → 后厨制作 → 交付配送 → 终态积分/库存处理 → 补货闭环。同时逐个讲了关键机制：店长维护商品+BOM、促销配置（如疯狂星期四）、下单时实时匹配促销并写成交价快照、支付成功后两段式积分（先记待生效）、下单即锁定原料防超卖、制作完成才实扣库存、终态触发积分到账与升级、扣库存后低于安全库存线自动生成补货建议单。并让AI优化了两份设计清单和提出建议。

**AI 做了什么：** 把这套口述整理成结构化的业务流程与机制点描述；随后帮用户一起把两份设计清单优化成型——
- 角色与职能清单：分"后台 / 门店作业 / 顾客 / 系统自动行为"四类，逐角色列职责、触碰数据与权限边界建议，其中把系统自动行为单独拎出来作为权限主体。
- 数据边界清单：按"进事实与快照、不进实时态与过程态"的原则，列出必须入库、不进库和灰色地带三部分及理由。

**我的处理：** 逐条对照真实门店经营核对内容；散客是否按手机号建档等灰色地带由我确定；清单确认后作为后续设计与建库的依据。

## （2026-09-09）——清单落盘 + 业务流程一致性审查 + 术语收尾

**聊了什么 / AI 做了什么：**
1. 把两份清单固化为仓库里的 markdown 文档（docs/），并整理 README 索引。
2. 我提交了《业务流程》文档，请 AI 与我之前提交的已有设计比对找冲突。AI 逐段核对后报告：主流程状态机（待支付→已支付→制作中→待取餐/待配送→配送中→已取餐/已完成）和成交价快照、两段式积分、锁定转实扣、安全库存线补货等机制都与设计一致；**唯一的实质冲突是"防超卖锁库的时点"**——角色清单/蓝图写的是"下单即锁"，而《业务流程》把锁库写在支付环节。此外指出流程里缺了"取消 / 退款 / 锁释放"整段。
3. 我采用**下单即锁**。AI 据此改《业务流程》：把锁库动作移到"下单确认生成订单"那一刻（锁定量↑、现有量不变、可售量↓），支付环节只保留积分预计算；新增第 8 步"异常路径"（未支付超时/取消 → 释放锁、订单置已取消；已支付在实扣前取消/退款 → 释放锁；退款同时冲销待生效积分流水）；补上外送"送达确认时记录送达时间"。
4. 术语收尾：统一全项目库存说法为**账面量（现有量）/ 锁定量 / 可售量（=现有量−锁定量）**，清掉含糊的"可用库存"；修了清单文件改名导致的 README 失效链接；修正一处从积分流水行复制错到配送记录行的理由文字。

**我的处理：** 锁定时点这类业务决策由我决定；AI 对文档的每处修改我都确认过，部分措辞由我自行再改。
