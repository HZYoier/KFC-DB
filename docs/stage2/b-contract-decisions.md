## 1. OI-09：基数总口径（B 已定）

图的端点统一表达 **DDL 能保证的结构基数**，业务最小数量/条件写在边标签和规则映射，不用端点把过程保证伪装为声明式约束。
某端的符号表示对端每行对应本端几行：非空子FK→父端恰好1，可空→父端0..1；父侧有多少子行由子FK的唯一性决定，PKFK/非空唯一FK使子端0..1，否则0..N。
例：PurchaseOrder→PurchaseOrderItem 子端应为ERzeroToMany；“审批原子生成恰好1明细”写标签。SalesOrder→SalesOrderItem同为物理0..N，业务成功订单至少1条SELLABLE。
这与B图、A图的结构口径及计划§4一致。C可据此更新legend和C图r6；B不改C图。OI-07端点方向措辞已由C修正，不再作为待修缺陷。OI-09状态仍由C确认跟进后更新。

## 2. OI-10 待决一：查单明细（B 已定）

`sp_customer_list_orders` **仅返回契约§1.4的订单头，一个结果集**；本阶段不附明细，也不新增第四个顾客过程。理由：头信息足以支持本轮查状态/金额/取餐码；保持C已确认“仅三个EXECUTE”的最小授权。
不采用草案中的 `sp_customer_list_order_items @order_id,@mobile`：手机号和可枚举订单ID不构成已同意的“手机号+取餐码”验证，另加该过程还需C扩大授权，不能当B单方面的小修改。
若未来确需明细，应在通过双要素定位的同一过程内增加第二结果集，或另开必须携带相同双要素的受限接口，并重新冻结返回列/权限；不把该扩展列入当前交付。
无匹配返回空结果，不能先抛53001/53002泄露手机号状态；内部只读过滤同时限定手机号、有效查询码和顾客启用状态。停用后的顾客查询也空集合，建档/下单的错误码行为另按契约处理。

## 3. OI-10 待决二：取餐码（B 已定自取规则）

### 可合入§1.3的文本

1. 自取码采用服务端生成的20位十六进制大写字符串：等价于 `UPPER(LEFT(REPLACE(CONVERT(VARCHAR(36), NEWID()), '-', ''), 20))`。格式 `[0-9A-F]{20}`，与现有员工下单“GUID去连字符截20位”的来源兼容，不承诺NEWID具备密码学随机性或完全80位独立熵。
2. 唯一范围是现有SalesOrder过滤唯一索引中全部非NULL取餐码，不只当天、不只未完成单；不得每日重用。最终防重由 `UQ_SalesOrder_pickup_code` 保证，不能只先SELECT查重。
3. 调用 `cust_app` 时非NULL的 `@pickup_code` / `@order_no` 拒绝为53000；这两个保留参数不是让浏览器决定订单凭据的入口。服务端生成订单号与码，并在订单提交成功后返回；出现2627/2601冲突则整笔回滚，返回E_CONFLICT，当前不承诺过程自动重试。
4. 查询只接受trim后20位十六进制码并转为大写；手机号trim后精确匹配。缺失/格式非法为53000；格式合法但不匹配为空集合。SQL参数绑定，不做模糊前缀查询。
5. 不把取餐码写入通用访问日志、错误响应、URL查询参数或其他顾客列表；表单用POST或同等避免URL泄漏的请求。该双要素是课程方案，不等于完整顾客身份认证，不为顾客加登录表。
6. `@ordered_at` 正常顾客调用必须NULL，不能从浏览器传历史时间；不借此冒充test_*。生产取当前数据库时间。

### 不能掩盖的履约边界

既有CHECK要求DELIVERY订单pickup_code为NULL，而顾客查询固定要求非NULL取餐码。当前三过程契约不足以让外送顾客按相同双要素查单。
B推荐本轮顾客入口只开放PICKUP，员工侧外送流程不变；非PICKUP顾客请求建议53000拒绝。但这涉及C顾客页范围，**作为待A/C确认的收敛建议，不冒充全组已批准限制**。
若A/C必须开放顾客外送，就先冻结独立查询凭据或经确认的手机号+订单号协议，不将外送码硬塞进pickup_code违反现有CHECK，也不擅自改共同契约。OI-10三项B技术决定已给出，但此履约边界与下列依赖仍需共同确认，不能宣称全条已关闭。

## 4. OI-10 待决三：锁库规则（B 已定，可合入§1.3约束4）

1. 下单过程在同一外层事务中校验启用顾客和有效商品，调用A唯一的 `fn_get_effective_product_price` 取得成交价/促销命中，写订单、SELLABLE父项及COMPONENT快照；组件数量已含套餐份数，组件零价，不由调用方提供。
2. 总额仅对SELLABLE执行高精度SUM(quantity×unit_price)，检查可表示范围后写DECIMAL(10,2)，不得将组件重复计价。
3. 然后调用现有C接口 `sp_lock_order_inventory @order_id`，不调用有员工身份守卫的 `sp_create_order`，也不由B直接更新Inventory。C按本单“SELLABLE单品+COMPONENT子项”各自的BOM汇总原料需求；套餐SELLABLE父项不再展开一次。
4. C检查不存在本单既有LOCK/RELEASE/CONSUME，拒绝无制作行、缺BOM、非正用量；以UPDLOCK/HOLDLOCK锁住所有涉及库存行，要求行齐全且on_hand_qty−locked_qty≥required_qty。
5. 成功仅增加locked_qty，不减少on_hand_qty；逐原料写LOCK流水：on_hand_delta=0、locked_delta=required_qty、reference_type=ORDER、reference_id=本order_id。
6. 顾客下单不得顺便支付、制作、实扣或生效积分；任何定价/插入/锁库失败，订单、父子明细、库存锁/流水一并回滚。C嵌套保存点不提交B外层；不可提交事务由最外层完整回滚。原C错误50000保留到后端日志，前端按共同E_RULE映射。
7. 同一批库存两单竞争必须在持锁后校验，不能“先在页面看可售量，插单后直接锁”。组件/原料汇总口径不因顾客账户而另写一套。

C现有锁库过程没有EmployeeAccount岗位守卫；通过dbo所有权链可供B专用过程内部调用。保持cust_app对锁库过程无直接EXECUTE权限，权限组合须在隔离副本由C用真实主体/EXECUTE AS USER正反例验收，不能仅凭源码称授权已跑通。
