# B 域函数依赖与规范化分析

> B；2026-10-14。2.2 提前分析稿，非全组设计冻结、非迁移完成。依据 R6-03/04/05/08/13/14/15/16。
> 输入：[B 问题清单](b-issues.md)、[订单字典](../订单履约数据字典.md)及 02/05/07b 源码。对业务合法状态与仅 DDL 允许的状态分别论证。

## 1. 判定方法

候选码是能唯一确定整行的最小属性集；代理主码也是候选码。“没有其他候选码”不能简称“没有候选码”。
过滤唯一且可空的 pickup_code 仅是部分行的标识，不按全关系候选码使用。
1NF：五表每列为单值，JSON 仅下单输入，不是订单表多值列。
2NF：所有已确认候选码均为单属性，因此不存在对候选码真子集的部分依赖。不能据此跳过 3NF。
3NF：每个非平凡 FD X→a，X 是超码或 a 是主属性；BCNF 更要求决定因素是超码。FD 来自业务规则，不从三个种子订单的偶然相等推出。
以下“全部其余属性”指原字典全部列，不是只分析图中的键列。

## 2. 逐表结论

| 关系 | 已确认候选码 | 关键 FD | 1NF / 2NF | 3NF 判断与处理 |
| --- | --- | --- | --- | --- |
| SalesOrder | {order_id}、{order_no} | 两码分别 → 全部其余属性 | 满足 | 就已识别的行内 FD 满足；total_amount 是跨关系聚合冗余，单独维护，不自动判 3NF 失败 |
| SalesOrderItem | {order_item_id} | order_item_id → 全部其余属性；product_id ↛ 历史 unit_price / promotion_id | 满足 | 普通全表无已确认非键一般 FD；COMPONENT 子集另有 parent_order_item_id → order_id 等条件依赖，故不能无条件宣称严格规范化无冗余 |
| Payment | {payment_id}、{order_id} | 两码分别 → 全部其余属性 | 满足 | 已识别行内 FD 满足；与订单金额相等是跨表不变量；third_party_txn_no 不是候选码 |
| Delivery | {delivery_id}、{order_id} | 两码分别 → 全部其余属性；rider_employee_id ↛ order_id | 满足 | 已识别行内 FD 满足；订单状态与配送状态的条件对应需事务维护，不等于两个关系应合表 |
| PointLedger | {point_ledger_id}、{order_id} | 两码分别 → 全部其余属性；{paid_amount_snapshot, point_multiplier_snapshot} → point_delta | 满足 | 按固定公式的业务语义，二元决定因素非超码、point_delta 非主属性，严格 3NF 不满足；明确保留受控反规范化 |

PointLedger 的公式不是“输入值相同恰好算出同值”的样例推测，而是冻结业务规则；两个不同订单可以有相同实付与倍率，所以这对属性不是码。仅 DDL 的 >=0 约束并不落实该 FD，说明数据库允许的关系状态比业务状态宽，不说明公式冗余消失。
COMPONENT 子集的 parent→order 是条件依赖；由于 SELLABLE 的 parent 为 NULL，不能不加条件把它当全表普通 FD。分析该子类型能揭示重复 order_id 的维护风险，但不能用 SQL NULL 直接套经典关系分解证明。

## 3. 插入、修改、删除异常逐表检查

以下是构造反例/边界推演，不是本轮执行结果。

| 表 | 插入例子 | 修改例子 | 删除例子 |
| --- | --- | --- | --- |
| SalesOrder | 手工只插订单不插明细产生空订单；过程拒绝 [] 且原子插入避免正常入口异常 | 明细 2×10.00 改成 3×10.00，主表仍 20.00；正常入口禁止改已冻结明细 | 删除订单会破坏支付/流水归属，FK 限制及岗位无 DELETE 阻止；不靠删单处理退款 |
| SalesOrderItem | 跨订单 parent 仍存在，单列 FK 可能接受；过程仅用本次 @parents 构造避免 | 后台改当前 Product 价格不应改历史 unit_price；正常接口无历史明细更新入口 | 删除最后一个 SELLABLE 会留空订单，父 FK 不能防止；权限和过程边界保证 |
| Payment | 同单第二笔支付被 order_id UQ 拒绝；不把多次网关尝试挤入此表 | 手改 paid_amount 会与订单/积分失配；退款只改退款字段、保留实付快照 | 删除支付会丢对账事实；业务退款保留行改状态，岗位无 DELETE |
| Delivery | 自取单也能在纯 DDL 下引用成功，过程仅为外送完成制作创建 | 将 rider_employee_id 改为其他骑手可能泄漏履约归属；认领/送达核验当前身份与锁 | 删配送会使外送订单无法闭环；业务入口不提供 DELETE，已送达事实保留 |
| PointLedger | 同单第二笔被 UQ 拒绝；两个独立 FK 仍不能防止错误顾客，过程从订单取值 | 10.00×1.50 原为15分，单改倍率成2.00却仍15分，形成真实公式更新异常 | 删流水不会自动减 Customer 累计分；业务只作废未生效流水，不提供删除 |

这些防护是“正常业务入口避免异常”，不是 DBA 任意写入也绝对安全。

## 4. 总额的两方案与推荐

- 保留：订单关联获取总额；支付/退款不必各自改为聚合查询，兼容现有接口。代价是必须原子维护、禁止任意改明细并逐单对账。
- 移除：由冻结的 SELLABLE 明细计算总额；代价是升级支付/退款/详情/调用方及基线协议，并处理并发读一致性。
- B 推荐保留。不拿没有实现的订单级优惠或未经测量的性能收益当依据。推荐依据是现有消费者与改动面可明确验证，待 2.2 冻结确认。

精度：unit_price DECIMAL(10,2)，quantity 正整数；以高精度计算 SUM，检查非 NULL、非负和 <=99999999.99 后转换。不存在每行额外小数舍入；组件价零且不参与收入。退款保留原成交总额，不因退款把 total_amount 清零。

## 5. PointLedger 的分解证明与取舍

设 P = 实付快照，M = 倍率快照，D = point_delta，F = {订单键→整行，(P,M)→D}。
理论分解为 R1 = PointLedger − {point_delta}，R2(P,M,D)。R1 保留 point_ledger_id 和 order_id 两个候选码，以及 P、M 和除 D 外的全部原属性：
- 交集是 {P,M}，且 (P,M)→R2 全部属性，满足二元分解无损连接条件；
- 订单键依赖及 (P,M)→D 在投影依赖闭包中保持，可由订单键→P,M→D 推回原关系；
- 该证明针对满足公式且无 NULL 的业务关系，不能对已有错误数据无条件成立。

但把所有金额/倍率组合建实体 R2 并无独立业务对象，还需维护公式结果字典。若改为查询/计算列派生 D 则是另一种实现，不等同于上述持久化二表分解。
B 推荐保留 D 为事件积分值，公开 3NF 取舍；写入时唯一计算，完成时使用快照 D，回归核对公式。未来积分公式变更须另设计规则版本，当前不提前加未定义字段。

## 6. 套餐子类型与积分累计的边界

若未来把 COMPONENT 独立为“父明细、子商品、数量”关系，应明确子类型键、父行唯一性和同单约束，并证明可重建原明细与角色；现在不实施，避免 C 库存消费者同步变更。
Customer.current_points 与订单总额分别论证。2026-10-24已核实09a给顾客2/3预置500/1500期初分，没有对应PointLedger；因此A新稿虽决定保留物化，其“完全等于本库EFFECTIVE之和”断言须修订。B采用期初offset加增量对账，见[重构汇总](refactoring-design.md) §7.1，不删除余额或伪造期初订单。双方仍需分别给FD、维护协议与消费者影响，不要求同时删冗余。
