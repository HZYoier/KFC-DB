# 门店运营系统操作手册（第二阶段 v1.0）

> 日期：2026-11-03；属主：A；适用版本：`SchemaVersion = v1.0` 的 `KFC_DB`。
> 口径：**只写已经能点到的界面**。订单与履约、顾客端页面尚未交付，§6、§7 只写当前状态与已冻结的接口，不描述不存在的按钮；页面到位后在本文件续写，不改已写章节的编号。

## 1. 运行环境与启动

### 1.1 前置

| 项 | 要求 |
| --- | --- |
| 操作系统 | Windows（本组三台机器均为 Windows） |
| 数据库 | SQL Server，已部署 `KFC_DB`；`v0.1` 用 `sql/run_all.sql`，迁 `v1.0` 用 §1.4 的顺序 |
| 驱动 | **ODBC Driver 18 for SQL Server**，三台机器同一版本，连接串里显式写驱动名 |
| Python | 3.11 及以上（本机实测 3.13.12）；依赖用 `pip install -r requirements.txt`（Flask 3.1.3、pyodbc 5.3.0，精确版本） |

### 1.2 配置

复制 `config.example.env` 为 `.env`（**`.env` 不进仓库**），按本机改：

| 键 | 说明 |
| --- | --- |
| `KFC_DB_SERVER` | 实例名：`localhost` / `localhost\MSSQLSERVER2` / `.\SQLEXPRESS` |
| `KFC_DB_NAME` | 库名，默认 `KFC_DB` |
| `KFC_DB_DRIVER` | 驱动名，必须是 Driver 18 |
| `KFC_DB_ENCRYPT` / `KFC_DB_TRUST_CERT` | Driver 18 默认强制加密；本机自签证书要 `TRUST_CERT=yes`，演示环境改用可信证书并置 `no` |
| `KFC_DB_QUERY_TIMEOUT` | 查询超时秒数，默认 30 |
| `KFC_SECRET_KEY` | 会话签名密钥。不填则每次启动现生成一把，**重启后要重新登录**；演示环境请填固定值 |
| `KFC_DB_TRUSTED_CONNECTION` | 仅本机冒烟用 Windows 信任连接。**演示环境必须 `no`**：此时 `USER_NAME()` 是 `dbo`，映射不到 `EmployeeAccount`，所有员工过程都会按「操作人未映射」拒绝 |

### 1.3 启动

```bat
python run.py
```

默认 `http://127.0.0.1:5000`；可用 `KFC_APP_HOST` / `KFC_APP_PORT` / `KFC_APP_DEBUG`（`1`/`true`/`yes` 开调试与自动重载）覆盖。启动只建应用，不建库、不改库。

### 1.4 数据库状态与迁移顺序

| 状态 | 判定 | 说明 |
| --- | --- | --- |
| v0.1 | `SchemaVersion` 无 `v1.0` 行 | 第一阶段对象，迁移前 |
| v1.0 | `SchemaVersion` 有 `v1.0` 行 | 迁移完成，页面按本手册操作 |

迁移三步（仓库根目录，`-b` 遇错退出）。**采集前必须先停应用**，采集期间不要再写库：

```bat
sqlcmd -S localhost -E -C -f 65001 -b -i sql/stage2/capture_baseline.sql ^
       -v SourceBaseline="<v0.1 的提交号>" -v ConfirmAppStopped=YES
sqlcmd -S localhost -E -C -f 65001 -b -I -i sql/stage2/run_migration.sql
sqlcmd -S localhost -E -C -f 65001 -b -I -i sql/stage2/regression.sql
```

第一步少给 `SourceBaseline` 或 `ConfirmAppStopped` 会被入口守卫拒绝——这两个变量不是可选项。

第二步在**一个外层事务**里串 `11a → 11b → 11c → 12`，任何一步失败整体回滚并报错，库仍是 v0.1。第三步必须在第二步**提交后**跑，它按 `SchemaVersion('v1.0')` 行取批次号。

### 1.5 账号

每位员工必须**用自己的数据库登录**连接：员工侧过程一律按 `USER_NAME()` 映射 `EmployeeAccount`（要求 `ACTIVE`，多数还要求岗位匹配），共用部署账户会让所有过程落到 `51004`。员工侧库登录由管理员按 `sql/stage2/provision_employee.template.ps1` 建，口令不入仓库。

## 2. 登录与退出

- 打开 `/login`，填**数据库登录名**与口令。口令只保存在服务端进程内存的会话表里（**8 小时**过期），不落库、不写日志；退出登录或进程重启即清除。
- 成功后进 `/`：显示姓名、登录名、岗位、业务角色（可多个）与权限码数量（可展开）。
- 会话有效期 **8 小时**；过期或重启（未设 `KFC_SECRET_KEY`）后需重新登录。右上「退出登录」立即失效。
- 登录失败的三种提示：

| 提示 | 含义 |
| --- | --- |
| 账号或口令不正确，或账号已停用 | `EmployeeAccount` 没有 `ACTIVE` 行，或口令错 |
| 数据库暂时不可用，请稍后重试 | 连不上实例、驱动缺失、证书不受信任 |
| 请输入数据库登录名和口令 | 提交时为空 |

## 3. 岗位与入口

| 岗位（角色码） | 现在能做什么 | 入口 | 状态 |
| --- | --- | --- | --- |

| 值班经理（`shift_manager`） | 库存看板与流水；补货建议新建/改量/提交；收货 | `/inventory/` | **可用** |
| 收银员（`cashier`） | 商品价目与顾客查询的数据库接口已就绪（契约 §2.4.2–2.4.4），页面未交付 | —— | 待 B |
| 厨师（`cook`） | 厨房队列与开始制作 | —— | 待 B |
| 配餐员（`packer`） | 制作完成、取餐 | —— | 待 B |

## 4. 店长：主数据维护

入口 `/master/`，九张卡片对应九个实体：

| 入口 | 实体 | 列表列 |
| --- | --- | --- |
| `/master/category` | 分类 | ID、名称、状态 |
| `/master/product` | 商品 | ID、名称、标准价、类型、状态 |
| `/master/ingredient` | 原料 | ID、名称、单位、安全库存、状态 |
| `/master/member-level` | 会员等级 | ID、等级名、积分倍率、门槛分、状态 |
| `/master/customer` | 顾客 | ID、手机号、类型、等级ID、等级、积分、状态 |
| `/master/bom` | 商品配方 | 商品ID、商品、原料ID、原料、用量 |
| `/master/combo` | 套餐组成 | 套餐ID、套餐、子项ID、子项、数量 |
| `/master/promotion` | 促销活动 | ID、名称、类型、开始、结束、状态 |
| `/master/promotion-rule` | 促销规则 | ID、活动、商品、星期、开始、结束、促销价、优先级 |

**筛选**：有状态列的实体可用 `?status=ACTIVE` / `?status=INACTIVE`；配方、套餐组成、促销规则**没有状态列**，带 `?status=` 会被过程拒绝，页面在提示条报「请检查输入内容」。

**动作**（18 个，每个实体页面下方是它自己的表单）：

| 实体 | 动作 | 填什么 | 规则 |
| --- | --- | --- | --- |
| 分类 | 新建 / 启停 | 名称；ID + 状态 | 名称 ≤ 50 字且不可重名 |
| 商品 | 新建 / 改价 / 启停 | 名称、标准价、类型、分类ID；ID + 新价；ID + 状态 | 类型只收 `SINGLE` / `COMBO`；金额 > 0、最多两位小数 |
| 原料 | 新建 / 修改 | 名称、单位、安全库存；ID + 全部字段 + 状态 | 名称与单位 ≤ 50 字；数量最多三位小数 |
| 会员等级 | 新建 / 修改 / 启停 | 等级名、积分倍率、门槛分；ID + 三字段；ID + 状态 | 倍率 > 0、两位小数；**门槛分允许 0**（默认档） |
| 顾客 | 建档 / 调档 | 手机号、类型；ID + 等级ID | 手机号 11 位数字；类型只收 `GUEST` / `WOW` / `PAID`；重复手机号报冲突 |
| 商品配方 | 设配方 | 商品ID + 每行 `原料ID 用量` | 用量最多三位小数；**空文本 = 清空该商品配方** |
| 套餐组成 | 设组成 | 套餐ID + 每行 `子项ID 数量` | 数量是正整数；空文本 = 清空 |
| 促销活动 | 新建 / 启停 | 名称、类型、开始、结束；ID + 状态 | 结束必须晚于开始；时间按 `YYYY-MM-DDTHH:MM` |
| 促销规则 | 新建 / 修改 | 活动ID、商品ID、星期、开始、结束、促销价、优先级；规则ID + 后五项 | 星期 1–7；时间 `HH:MM` 24 小时制；优先级可 0，数字越大越优先 |

**配方与套餐的填写格式**：一行一条，ID 与数量之间用空格、逗号或冒号分隔都可以，空行忽略。例：

```
1 0.25
3,0.500
```

**错误提示条**：输入不合法 400「请检查输入内容」；重名、重复手机号等唯一约束 409「数据与现有记录冲突」；过程里的业务规则 409「操作未完成，原因见提示」；越权 403「当前账号无权执行该操作」。列表页只经过程取数，**没有对任何岗位开放基表 `SELECT`**。

## 5. 库存与补货

入口 `/inventory/`，一页三块：库存看板、库存流水（可按原料 ID 过滤）、补货建议。

| 操作 | 谁能用 | 填什么 | 规则 |
| --- | --- | --- | --- |
| 调整库存 | 店长 | 原料ID、调整量（正负均可）、原因 | 调整量不能为 0，最多三位小数；原因必填、≤ 50 字 |
| 新建补货建议 | 值班经理 | 原料ID、建议数量 | 数量 > 0，最多三位小数 |
| 修改建议数量 | 值班经理 | 建议ID、新数量 | 同上 |
| 提交审批 | 值班经理 | 建议ID | 提交后等店长审批 |
| 审批 / 驳回 | 店长 | 建议ID；驳回还需原因 | 驳回原因必填 |
| 收货 | 值班经理 | 采购单ID、实收数量（可空） | 数量 > 0 |

按钮按角色显示，但授权与状态机都在数据库过程里；状态不对（如审批已提交前的单子）会按过程定义报错，页面照原样显示提示。

## 6. 订单与履约（收银 / 厨师 / 配餐 / 骑手）

**当前状态：页面未交付。** `app/orders/` 目前只有 `dao.py` 与 `service.py`（下单、支付、开始/完成制作、自取、骑手认领/送达、取消退款八个动作），没有 `routes.py` 与模板，所以本章没有可操作步骤可写。

已冻结、页面到位后可直接用的口径：

- 收银取价可调 `sp_list_sale_products`（`@take` 只收 1..200，越界报错不静默截断），但**展示价不替代订单快照**：落单金额仍由 `sp_create_order` 记录。
- 顾客查询用 `sp_find_customer_for_order`（精确手机号、查不到返回空集合）；临时建档用 `sp_register_customer_for_order`（固定 `GUEST`、0 分、默认等级；重复手机号报冲突）。
- 支付后网络中断属于**结果未知**：先查订单与支付状态，再决定是否重新发起，不自动重复写入。

页面交付后在本章补：收银下单与收款、后厨开始制作、配餐出餐与取餐、骑手认领与送达、店长取消与退款。

## 8. 常见问题

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 登录提示「账号或口令不正确，或账号已停用」 | 没有 `ACTIVE` 的 `EmployeeAccount` 行，或口令错 | 找管理员核对账户与口令，不要用 `dbo` 试 |
| 页面提示「当前账号无权执行该操作」 | 该岗位没有该过程的 `GRANT`（`229`），或岗位不符（`51004`） | 换对应岗位的账号；不要靠改页面绕过 |
| 「数据与现有记录冲突」 | 名称/手机号重复，或唯一约束被撞 | 先查列表确认已有记录，再换值 |
| 「操作未完成，原因见提示」 | 过程里的业务规则没满足（状态机、数量、配额） | 按提示纠正输入；提示文案不透露库内细节 |
| 「系统暂时无法完成操作」 | 连不上实例、驱动缺失、证书不受信任、超时 | 检查 `.env` 与 SQL Server 服务；本机自签证书要 `TRUST_CERT=yes` |
| 控制台中文乱码 | 通常是 `sqlcmd` 显示层，不是库里的中文坏了 | 脚本加 `-f 65001`；证据用 `-o` 写文件 |
| 重启后要重新登录 | 没设 `KFC_SECRET_KEY`，每次启动现生成密钥 | 在 `.env` 里填固定值 |
| 提交后列表没变 | 页面重定向后有缓存或看的是旧筛选条件 | 刷新；仍不对就看提示条与日志 `request_id` |
