# B 详细测试用例与执行规程

> B；2026-10-14；覆盖[事务矩阵](transaction-boundaries.md) BT-01—BT-11。
> 全部为待实施测试设计，**本轮没有运行数据库或应用测试**。先有隔离副本与授权夹具，再实现 13b/Orders 测试；不能把文档数量写成 PASS 分母。

## 1. 测试环境与夹具

部署冻结 v0.1 或迁移后的 v1.0 副本，记录提交/版本、实例、驱动、认证方式、实际对象摘要。SQL 用 test_* WITHOUT LOGIN 验证过程逻辑；应用用真实独立员工登录，不混用两种验收身份。
角色至少 CASHIER、CHEF、PACKER、两个不同 RIDER、STORE_MANAGER、WAITER；C 提供映射与授权。一个员工不要临时改 job_code 假装多岗位。
A 提供/确认顾客 G（ACTIVE，等级 ACTIVE、倍率 M>0）、有效单品 P1/P2、有效套餐 K、促销窗口。非促销数值案例使用 P1=10.00、P2=4.00、K=18.00，组成 P1×1+P2×2；这些是测试夹具目标，不硬编码已有 product_id 或假定当前主数据就是这些价格。
C 提供所需 BOM、足量库存与原料集合 I，库存不足案例另用隔离夹具。应用不能通过自己增改 A/C 表造数；部署级受控夹具按现有测试例外在回滚事务内运行。
订单号带唯一用例前缀与随机后缀，<=50 字符；数组由真实 P/K 数字 ID 序列化，只传 product_id、quantity。每例记录开始前库存/流水/顾客/订单键集合，不用全库行数差推断本例成功。

### 统一操作与收尾

1. 建立 FRESH 夹具，确认所有前置条件，否则标 BLOCKED（夹具未满足），不能记 PASS。
2. 记录本例外层 @@TRANCOUNT、关键事实快照；以指定主体调用真实过程。
3. 捕获精确错误号与原始消息；预期 THROW 可能令 XACT_STATE=-1，先整体回滚，再恢复模拟身份、用新连接/安全会话查后态。
4. 正常路径在隔离副本内核对数据，然后清理夹具或回滚。已提交跨连接/并发/网络案例由部署者恢复专用副本，不能业务直删账目或重建共享库。
5. 缺少异常、错误号不符、任何半成功、清理失败都 FAIL。结果不确定标 INDETERMINATE，不可记 PASS；故障注入代码不进入生产接口。

## 2. BT-01 输入拒绝（四个独立断言）

| 子例 | 前提/身份与输入 | 操作 | 精确预期 | 后态/清理 |
| --- | --- | --- | --- | --- |
| BT-01a | CASHIER，G有效；items_json=[] | 新号调用 create | 52105；消息含 nonempty array | 无本号订单，无本例库存/流水差异；回滚 |
| BT-01b | CASHIER，根为 {} 或非法 JSON | 分别 fresh 调 create | 两种分别 52104 | 无订单/明细/LOCK；各自回滚 |
| BT-01c | CASHIER，数组项增加 unit_price 或重复 product_id 键 | 各自调用 create | 分别 52106 | 不接受客户端报价；无副作用 |
| BT-01d | CASHIER，quantity=0 或超 INT 正整数 | 各自调用 create | 分别 52107 | 不出现溢出后的合法订单；无副作用 |

重复键需用原始 JSON 字符串构造，不能先经会去重键的字典序列化。quantity 的负数/小数可能更早命中 52106，不误期待所有非法数字均为 52107。

## 3. BT-02 价格、套餐与历史快照

- 前置：足量库存、G、P1/P2/K，A 确认测试时间无促销；测试主体可用 test_cashier 传受控时间。
- BT-02a：下单 P1×2、P2×1；应有两个 SELLABLE、总额 24.00，明细价格 10.00/4.00，与 A 函数结果一致。C 锁量按两商品 BOM 聚合，不按商品行数计。
- BT-02b：单独下 K×2；一 SELLABLE 父项价 18.00、数量2、总额36.00；两个 COMPONENT 分别 P1数量2、P2数量4，父键正确、价格0、促销NULL。A BOM 展开与 C LOCK 原料需求一致。
- BT-02c：在 A 批准的回滚夹具中调整当前商品价；原订单 unit_price/promotion_id/total_amount 不变。新的下单价可变化，但不得反算旧订单。
- 收尾：每例独立回滚；读取 A/C 前后事实无残留。没有批准改价夹具时 BT-02c 标 BLOCKED，不替 A 改生产商品。

## 4. BT-03 库存不足原子回滚

前置：C 在副本构造某原料可售量小于需求，其余下单条件全部合法；C 确认错误注入点确为库存不足。
操作：CASHIER 调 create。
预期：当前源码 50000，原始消息包含“可用库存不足”；若 v1.0 经冻结改码则按契约更新，不自行吞错。
后态：本号订单/父子明细均不存在，Inventory 的 on_hand/locked 和 InventoryMovement 与前态相等；不能只看 B 行数。整体回滚后查询、核对清理。

## 5. BT-04 支付边界与快照（三子例）

前置：分别创建总额24.00的待付单；G倍率 M 由夹具读取。
- BT-04a：付23.99，期待52202；订单仍待付，无 Payment/PointLedger；库存锁没有因失败额外变化。
- BT-04b：付24.00成功，再相同参数支付一次；第二次期待52201（状态检查先于52204）；仅一支付、一积分。积分=FLOOR(24.00×M)，ledger为PENDING，顾客累计尚未增加。
- BT-04c：第三方流水号显式DBNull，方式传非空值；成功存NULL。应用省略无默认参数属于调用契约失败，不能当数据库支持省略。
每子例 fresh；异常子例先回滚再查态。不得把一次成功支付随后测试异常导致的外层整体回滚误写成生产首次支付丢失。

## 6. BT-05 积分入账故障与正常完成

前置：完成自取所需制作，订单READY_FOR_PICKUP、流水PENDING。A/C 在隔离副本批准可识别的入账异常方案；记录顾客分数/等级、订单/流水和库存。
操作：PACKER 调 pickup；A 入账点失败。
预期：原异常编号/消息传播；订单仍READY_FOR_PICKUP、completed_at原值，积分仍PENDING，顾客分数/等级未变；此前已提交制作实扣不应被补回。
恢复故障后另 fresh 正向调用：订单PICKED_UP、积分EFFECTIVE，顾客累计增加恰好delta；再取餐期待52501且不重复入账。外送完成路径同类独立覆盖，配送/订单/积分必须一起回滚。
故障编号由 A 实际方案给出并记录，不预造一个新公共错误码。

## 7. BT-06 实扣/退款审计故障（两子例）

- BT-06a：订单IN_PRODUCTION；C 在副本让 consume 的可识别点抛错；PACKER 调 finish。期待原C错误；订单/production_finished_at不变、无新Delivery，库存/CONSUME/补货建议与前态一致。
- BT-06b：已支付未实扣、积分PENDING；C 在副本让 audit 抛错；STORE_MANAGER 以REFUND取消。期待原C错误；订单仍原状态、Payment仍SUCCESS且退款0、积分PENDING、库存锁/RELEASE和审计均不留半成功。
恢复注入后独立正向退款：订单CANCELLED、PaymentREFUNDED且refunded_amount=paid_amount、流水VOIDED、锁释放、审计存在；再次退款期待52802。
故障注入与恢复由属主批准，不能在共享库 ALTER C 的过程。

## 8. BT-07 两骑手并发认领

前置：已提交的外送READY_FOR_DELIVERY、唯一Delivery WAITING_PICKUP且骑手NULL；两真实RIDER账号R1/R2。
操作：两个独立连接在屏障同时释放后调用 pick_up_delivery，各传自身ID；设置有限超时并记录两连接完成顺序、错误号及事务结果。
预期：恰好一个提交成功；失败方在状态重查时通常52602，若到配送保护检查则52603；只有已证明发生的死锁可记录1205并受控重试，不能将任意超时当正常竞争成功。
最终：订单DELIVERING，唯一配送骑手为胜者，流水/库存无额外变化；失败方 confirm 应52702（在订单仍DELIVERING时），胜者可正常完成。无双方都成功或一直阻塞。
独立提交案例不能靠单连接回滚清理，使用专用副本恢复。

## 9. BT-08 Common 外层事务与参数绑定

前置：A 提供 Common 同身份同连接 helper，CASHIER真实登录、G有效、足量库存。
操作：helper 内先 create 新号，再执行测试驱动中的显式故障；故障不新增生产过程。捕获异常后 helper 全部回滚、关闭连接。
预期：原订单/明细/LOCK均不持久化，顾客/库存前态保持；应用不能把过程内保存点释放当外层提交。
另检验BIGINT超INT范围的参数绑定、NVARCHAR(MAX)大于4000字符的合法数组构造（在有效单商品数组内加入合法JSON空白，不靠重复商品触发52108）、DECIMAL precision10/scale2、NULL显式绑定。BIGINT绑定使用类型检查或隔离夹具确认，不要求现有商品/顾客恰有超INT的ID。输入小数位超2或字符串超长须由应用拒绝，不能靠驱动静默舍入/截断后称精确。
第二次新连接正常调用成功证明异常后会话可用；这不替代真实数据库断线恢复测试。

## 10. BT-09 身份、越权与停用

- BT-09a：CASHIER直接改商品价格/库存/顾客积分，预期229且三处值不变；独立SQL反例每条精确记录。测试部署者不得用dbo冒充岗位通过。
- BT-09b：R2确认R1正在配送订单，预期52702、订单/骑手/积分不变；WAITER直接调用未获授权支付过程应229，而非仅看菜单不可见。
- BT-09c：应用CASHIER注销，改RIDER登录；上下文变为新员工、购物车/旧凭据清空；不再有收银功能或权限。C撤销/停用后下一次操作拒绝；具体编号以C上下文/GRANT是否保留为准，分别验证身份守卫与授权守卫，不混成一个固定码。
全部记录数据库主体USER_NAME、员工ID、岗位（不含密码），并复验受保护数据。

## 11. BT-10 响应丢失与结果确认

前置：B状态查询按[交接提案](b-interface-handoff.md)冻结并实现，A网络测试工具能区分“提交前断线”和“提交后响应丢失”；不在共享服务器中断服务。
- BT-10a：支付已提交但响应丢失，重新登录按order_id查到PAID/SUCCESS和原实付；不得自动再次付。订单及流水数量都保持1。
- BT-10b：下单已提交但客户端无order_id，以请求前保留的order_no精确定位；不得换新号重下。
- BT-10c：旧请求事务尚未结束时查询可能阻塞或尚无可见记录，应显示结果待确认；确认旧调用结束后用同号受控重试，最终唯一订单。不把一次查无结果等同“肯定没提交”。
查询输出不得含其他顾客档案。暂未实现该接口时标BLOCKED，不用给收银临时基表SELECT绕过。

## 12. BT-11 重复商品输入决议验收

当前基线：重复顶层P1两行→52108；K与其子P1同时顶层输入→52110；两个不同套餐共享子商品可生成不同父项下的相同product_id，DDL不加(order_id,product_id)唯一。
若选择[方案B](b-duplicate-product-decision.md)，替换这些断言为两售卖行/各父子归属/精确聚合并保留历史输入兼容；若选择方案A，记录教学解释及行合并边界。无决议时保持当前源码预期，不能写“已经支持重复售卖行”。

## 13. 结果记录与断言计数

每子例最小记录：case_id、版本/提交、身份、夹具键、脱敏参数、预期与实际错误号/消息、前后事实、PASS/FAIL/BLOCKED/INDETERMINATE、清理状态、证据路径、退出码。
一个分组含多个子例时逐项计数；实际脚本冻结后才给预期断言分母，不把BT组数11当11条测试。C汇总脚本必须对FAIL/清理失败返回非零，对BLOCKED/未跑不能发布“全通过”；网络案例记录未知态到最终闭环的完整时间线。
