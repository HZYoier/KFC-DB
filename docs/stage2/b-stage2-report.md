# 成员 B 第二阶段个人实验报告：订单模块

> 24325328 张奕希｜2026 年 11 月 8 日

## 1. 实验目标

第一阶段已经把下单、付款和履约写成了存储过程。这一阶段我要做的是让收银、配餐和骑手能在各自的页面上查到该看的单、办完各自的业务，还要保证迁移不会把旧单的成交价、付款记录和积分改掉。我负责订单模块，不改 A 的定价、建档和共享连接层，也不改 C 的库存和授权实现。

## 2. 实验思路

订单的五张表保留原来的设计。比如套餐当前的售价变了，老订单仍要显示下单时的价格，所以不能用现在的商品表去反推当时的成交金额。我先把这五张表的 53 列做成按批次保存的快照。迁移后再逐表比较，金额和时间按原值比较，订单号按字节比较，避免数据库不区分大小写时漏掉变化。

查询按岗位拆。收银要看总额和售卖项，配餐要看套餐下有哪些组件，但不需要知道顾客资料和实付金额。配餐查询先确定本次要看的订单，再根据这批订单找明细，否则直接限制明细行数，可能只显示半个套餐。页面只负责把信息列出来并提交操作，能不能支付、退款或认领仍由数据库判断。

## 3. 实验过程

1. 对照冻结契约完成 [11b 迁移脚本](../../sql/stage2/11b_order_migration.sql)。新增六个员工查询和两个顾客过程，没改原有八个写过程的参数。顾客端只接自取；查单同时核对手机号和取餐码，查不到就返回空，不告诉调用方手机号是否存在。
2. 顾客下单时先检查商品，再用 A 的定价函数写成交快照，最后在同一事务里调用 C 的锁库过程。我故意把临时库的可用库存压到零再提交，核对失败前后订单头、明细、库存锁量和流水的数量，确认没有留下半张单。
3. 用 Flask 做了收银、厨师、配餐、叫号、骑手和店长的订单工作台（`/orders/`）。提交前就显示订单号，同一会话还能找回最近打开的表单编号。同一张表单重复提交时沿用原订单号，由数据库唯一约束拦住。实际测试先用收银账号下单并付款，再退出换厨师账号；厨师可以开始制作，但不能支付。工作台每次用 C 的接口核对当前身份，叫号员停用后即使还开着页面，再访问也会回到登录页。
4. 联调时遇到一个只在真实连接上出现的问题：不填第三方流水号，SQL Server 已经写完支付，驱动却在读结果时报游标错误。最初页面返回失败，但查询订单已经是已付款。这时重发支付不合适。我把页面改成遇到这个特定情况就重新查询，只有查到成功支付且金额一致才提示已付款。测试也查了支付表，确认只有一笔记录，流水号仍是 NULL。

## 5. 实验体会

这次最有用的是先查数据库，再判断页面上的报错代表什么。不填流水号时，光看页面会以为付款失败，但实际记录已经写进去了。另一个容易忽略的地方是套餐：收银看到的是卖出去的一份套餐，配餐看到的却是其中几个组件，同一个查询不能随便拿来给两个岗位用。以后如果要补顾客断线恢复，我会先把请求标识和重试规则定清楚，不靠多点一次下单按钮来解决。
