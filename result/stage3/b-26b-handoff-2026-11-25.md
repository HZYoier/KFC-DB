## 已验证结果

| 场景 | 业务过程与结果 | 轮数 |
| --- | --- | --- |
| 订单提交再放行补货 | 先下 P×2 订单并付款、开始制作。外层事务调用 `sp_finish_production`，P 从 10 变为 8。另一会话调用 `sp_receive_inventory` 加 5，被订单事务阻塞。订单提交后，补货完成，P=13，锁定量为 0，订单待取餐，采购单关闭 | 3 |
| 订单回滚再放行补货 | 同一形状，订单回滚后 P 恢复为 10，补货继续并加 5，最终 P=15。订单仍在制作中，原有锁定量 2 恢复，采购单关闭 | 3 |
| 两笔并发购买 P×6 | 两连接用屏障同时开始，通过真实下单、付款、开始制作、完成制作过程。成功方提交整单，失败方收到 C 锁库过程的 `50000` 与可用库存不足消息。最终 P=4、锁定量为 0，只有一笔完整订单和一组锁库、实扣流水 | 3 |

订单、补货、观察三个会话的 SPID 各不相同，记录了隔离级别、SQL Server 版本及 RCSI。等待关系通过观察连接从 DMV 读取，再由控制端提交或回滚订单事务。每轮使用新 P，Q 初值 8 并保持不变。整个隔离库在最后删除。

## 复跑入口

```powershell
.venv/Scripts/python.exe -X utf8 tests/stage3/b_programmability/run_b_stage3.py --sql-server 'localhost\MSSQLSERVER2' --verify-all --concurrency-v2
```

订单侧 SQL 在 `sql/stage3/26b_order_concurrency.sql`，支持三个步骤。

- `Mode=finish` 在调用方已开启的一层事务内完成指定订单，保留事务供协调者决定提交或回滚。
- `Mode=buy` 以新订单号原子执行 P×6 的下单、付款、制作和完成，成功提交，失败回滚。
- `Mode=lock` 在调用方事务内先取得 P 的更新锁，用于和 C 的补货 Q→P 步骤对接。

所有模式显式绑定 `IngredientP / OrderId / OrderNo / ProductId / CustomerId`。本轮 Python 夹具会替换这些 SQLCMD 变量，调用者需以部署测试身份运行。SQL 禁止在非 B 隔离库执行。

## C 侧尚需接入的联合死锁步骤

B 已提供 `lock → finish` 的订单侧步骤。联合场景需先构造含 P、Q 两种原料的已付款制作中订单，以及 C 的两笔审批后采购单。B 先执行 `lock` 锁 P，C 完成 Q 收货并暂不提交，再让 B 执行 `finish` 请求 Q，同时 C 收 P，捕获死锁图与 1205。

改进轮由双方在业务调用前依次对 P、Q 逐项 `UPDLOCK` 加锁，观察普通等待并确认两端完成。该步骤需要 C 按新版 §7.3 更新补货侧会话、取图和改进脚本。本轮没有把旧 26c 技术基线记为这项业务死锁验收，也没有宣称联合死锁改进已通过。
